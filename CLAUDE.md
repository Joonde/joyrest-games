# JoyRest Games — технический паспорт проекта

Этот файл читается в начале каждой сессии Claude Code. Он фиксирует архитектуру и правила.
Любое изменение архитектуры сначала вносится сюда, потом в код.

## 1. Что мы делаем

Интерактивная веб-платформа для ведущих агентства JoyRest (Москва): квизы и игры на
свадьбах, корпоративах, днях рождения. Гости играют со своих телефонов, вопросы
показываются на большом экране, ведущий управляет игрой с пульта.

- Типичное мероприятие: 20–50 гостей. Расчётный максимум: 500 гостей в одной сессии.
- Несколько ведущих работают одновременно, каждый в своих сессиях.
- Язык интерфейса: русский.
- Владелец проекта работает только с телефона: проверка идёт по тестовым ссылкам
  хостинга, а не локально. Всё, что нужно сделать руками, описывай пошагово для
  мобильного браузера.

## 2. Стек

- Vite + React + TypeScript (strict, без `any`).
- Firebase: Authentication (почта/пароль для ведущих, анонимный вход для гостей),
  Firestore (данные и синхронизация в реальном времени). Firestore работает с
  `persistentLocalCache` и `experimentalAutoDetectLongPolling` (медленные мобильные сети).
- Бесплатный тариф Spark: Cloud Functions и Storage не используем.
- Хостинг: Netlify с автопубликацией из GitHub (`netlify.toml`). Каждая ветка получает
  свою тестовую ссылку.
- Тесты: Vitest для логики, эмулятор Firebase для правил безопасности.

### Слой данных и возможный переезд (обязательное правило)

Возможен переезд с Firebase на свой сервер (Node.js + WebSocket на VPS в России). Поэтому:

- Всё, что связано с Firebase (Auth, Firestore, правила), — **только внутри `src/data/`**.
  Экраны, компоненты, механики и `src/core/` не импортируют `firebase/*` и внутренние
  модули слоя данных.
- Экраны и механики работают через интерфейсы `src/data/contracts.ts`: `AuthService`,
  `UsersRepository`, `GamesRepository`, `SessionsRepository`, `ParticipantsRepository`,
  `AnswersRepository`, `ResultsRepository`, `MediaRepository`, `ClockService`. Экземпляры (`authService`, `gamesRepo`,
  `sessionsRepo`, …) и типы берутся только из `src/data/index.ts`. При переезде пишется
  новая реализация тех же интерфейсов, остальной код не меняется.
- Логика прав («кто что может») продублирована в `src/data/permissions.ts` обычными
  функциями без Firebase и покрыта тестами (`permissions.test.ts`). Интерфейс решает по ним,
  что показывать; будущий сервер проверяет по ним запросы. `firestore.rules` и
  `permissions.ts` меняются только вместе, вместе с обоими наборами тестов.
- Тест `src/data/boundary.test.ts` проверяет, что вне `src/data/` нет импортов Firebase и
  внутренних модулей слоя данных (единственное исключение — загрузчик SDK в `main.tsx`).

### Переезд на свой сервер (идёт сейчас)

Платформа переезжает с Firebase и Netlify на свой сервер в России (VPS Beget, Ubuntu 24.04,
2 vCPU / 2 ГБ, 217.114.13.92, домен games.joy-rest.ru). Персональные данные (имена гостей,
почты ведущих), логи и бэкапы хранятся только в России. Пока идёт переезд, Firebase-версия
работает как раньше; после переключения Netlify перенаправляет на games.joy-rest.ru, данные
Firebase удаляются, Firebase-код удаляется отдельным PR.

Архитектура сервера:
- Docker Compose (`deploy/compose.yml`), проект `joyrest`: `caddy` (HTTPS для games.joy-rest.ru
  и сайта агентства joy-rest.ru, www → joy-rest.ru) → `app-prod` (Node.js 22 + TypeScript,
  Fastify: платформа, сайт агентства по Host, `/health`, `/api/lead`, дальше `/api` и `/ws`) → `postgres` (PostgreSQL 17, одна на
  основное и тестовое окружение, разные базы). У всех контейнеров `mem_limit`.
- Наружу публикует порты только `caddy` (80, 443, 443/udp). Docker обходит ufw, поэтому
  других `ports:` в compose быть не должно (проверяет CI). База — во внутренней сети.
- Код сервера — `server/`, собирается esbuild в один файл (`npm run build:server`).
  Сервер переиспользует `src/data/permissions.ts` и типы `src/data/types.ts`.
- Всё собирается в GitHub Actions (`.github/workflows/build.yml`): тесты → образ
  `ghcr.io/joonde/joyrest-app:sha-<коммит>` (сайт + сервер + `deploy/`). Сервер только
  скачивает образы из GHCR и ничего не собирает (2 ГБ памяти). Docker Hub с российских IP
  ограничен: базовые образы (`caddy`, `postgres`) копируются в `ghcr.io/joonde/joyrest-mirror/`
  (`mirror-images.yml`, раз в неделю), compose ссылается только на GHCR.
- На сервере: `/srv/joyrest/` — `secrets.env` (только на сервере), `releases/<коммит>/`
  (папка `deploy/` из образа), `current` → текущий релиз, `postgres/`, `caddy/`, `backups/`.
  Управление — команда `joyrest` (`deploy/bin/joyrest`), инструкции владельцу — `RUNBOOK.md`.
- Пользователи сервера: владелец (sudo, вход по ключу из Termius), `deploy` — без sudo и
  консоли, ключ GitHub Actions привязан к привратнику `deploy/bin/joyrest-gate`: он пропускает
  только `ping`, `status`, `deploy <40 hex> [force]`, `deploy-test <40 hex>` и кладёт запрос
  в очередь `/srv/joyrest/deploy/queue/`; выкладывает служба root (`deploy/systemd/`).
- Выкладка (`joyrest deploy`, `.github/workflows/build.yml`, задача `deploy`): main →
  games.joy-rest.ru, ветки `claude/*` → test.games.joy-rest.ru (`app-test`, база
  `joyrest_test`, `mem_limit` 256m). Шаги: блокировка → проверка игры → образ по отпечатку →
  дамп базы (`backups/predeploy`, 5 последних) → миграции (`server/migrations`, только
  добавляющие) → переключение → `/health` с новой версией → иначе откат на прошлую.
  Тестовое окружение общее (сайт и платформа): коммит ветки `claude/*` с `[no-test]` в
  сообщении на test не выкладывается (задача `deploy` пропускается, сборка, тесты и образ — как
  обычно; на `main` пометка не действует). Ставьте `[no-test]`, если test для проверки не нужен
  (например, команды `joyrest` и службы — они ставятся только из основного релиза). Решает
  сообщение последнего коммита в push.
  Два пути: SSH из Actions и запасной — тег `release`/`test-release` в GHCR, который сервер
  проверяет каждые 2 минуты (`joyrest-update.timer`, токен только `read:packages`). Итог
  Actions проверяет по HTTPS `/health` и пишет в Telegram. Включается переменной
  репозитория `DEPLOY_ENABLED=true`: задача «Переключатель выкладки» (`switch`) сравнивает
  её без учёта регистра, `\r\n`, пробелов по краям и невидимых символов (вставка с телефона)
  и при выключенной выкладке показывает в логе, что видит. Секреты Telegram и SSH тоже
  очищаются от пробелов и `\r\n`; причина неудачной отправки в Telegram пишется в лог.
- Блокировка выкладки во время игры: основная версия не выкладывается, если есть сессия с
  `phase in ('lobby', 'playing')` и `updated_at` за последние 30 минут. Если проверить не
  удалось (база не отвечает) — тоже считается, что игра идёт: статус `blocked`, таймер
  повторит. `force` — только вручную (Termius или Run workflow с галочкой); CI сам `force`
  не отправляет никогда, теги `release`/`test-release` ставит только при `DEPLOY_ENABLED`.
- **Миграции только обратно совместимы (expand/contract).** Они выполняются до переключения
  версии, а откат возвращает прошлый код, но не схему: новая схема обязана работать со
  старым кодом. Можно: новые таблицы, колонки с `DEFAULT` или без `NOT NULL`, индексы.
  Нельзя в обычной миграции: `DROP`, `RENAME`, смена типа, `SET NOT NULL`, `NOT NULL` без
  `DEFAULT`, `TRUNCATE`, `DELETE`. Удаление — отдельной contract-миграцией (первая строка
  `-- contract: <что и с какого релиза не используется>`), не раньше чем через релиз после
  того, как код перестал это использовать. Переименование = новая колонка + код пишет в обе
  + contract-миграция. Проверяет тест `server/src/migrationRules.test.ts`.
  Поэтому таблица `sessions` на сервере обязана иметь `phase` и `updated_at` (обновляется
  при каждом действии пульта).
  После проверки выкладки: `PermitRootLogin no`, `PasswordAuthentication no` (`lock-ssh.sh`).
- Первичная настройка: `deploy/setup/check.sh` (проверка связи, ничего не меняет) →
  `deploy/setup/install.sh` (система, ufw, fail2ban, автообновления, Docker, ротация логов
  Docker 10m×3 и journald 200 МБ/14 дней, запуск). Секреты показываются один раз.
- Резервные копии (`joyrest backup*`, `restore`, `deploy/systemd/joyrest-backup.*`): каждую ночь
  в 04:40 дамп `joyrest_prod` (проверенный `pg_restore --list`) → диск (`backups/daily`, 3) и restic
  → Beget S3 (зашифровано). Сроки: 7 ежедневных, 4 еженедельных, 3 ежемесячных (+ до недели до
  `prune`). Раз в неделю `prune`, `check --read-data-subset=10%` и итог в Telegram, раз в месяц —
  восстановление во временную базу; `prune` и проверки при игре (правило 30 минут) — на следующую
  ночь. Доступы — только `/srv/joyrest/backup.env` (пишет `sudo joyrest backup-setup`, пароль
  restic показывается один раз), `secrets.env` в копию не входит. Сообщения сервера — служебный
  бот (`sudo joyrest notify-bot` → `NOTIFY_TELEGRAM_*` в `secrets.env`, приложения его не видят).
  Основная база восстанавливается только из Termius с подтверждением, прежняя остаётся
  `joyrest_prod_before_restore`. Версионирования и object lock у Beget S3 нет. Проверяет
  `server/src/backup.test.ts`.
- Минуты Actions (закрытый репозиторий, 2000 в месяц) — только на сборку и выкладку.
  Внешний мониторинг «сайт недоступен» — UptimeRobot, не cron в Actions.

Этапы переезда (PR): 1 — инфраструктура; 2 — выкладка (SSH + сервер сам забирает релиз,
откат, тестовое окружение test.games.joy-rest.ru, блокировка выкладки при игре с активностью
за 30 минут); 3–4 — сервер (вход argon2 + httpOnly-cookie, токены устройств гостей с мягким
лимитом выдачи по IP, REST, WebSocket, права на сервере); 5 — клиент `src/data/server/` и
офлайн-очередь; 6 — бэкапы (restic → Beget S3, пароль restic и ключи S3 владелец хранит у себя)
и мониторинг (Telegram, UptimeRobot); 7 — нагрузка (не запускается при активной игре);
9 — переключение; 10 — удаление Firebase.

### Сайт агентства (joy-rest.ru)

- Исходники — `site/` (обычные HTML, CSS, JS без сборщика), материалы — `docs/site-extras/`
  (на сайт не выкладываются). `npm run build:site` (`scripts/build-site.ts`) собирает
  `build/site`: отпечаток содержимого в именах файлов `css/`, `js/`, `img/` и ссылки на них;
  шрифты — файлы платформы из `public/fonts/` (Google Fonts не подключаем); логотипы из
  `public/brand/` встраиваются в элементы `data-brand-svg="<имя>"` (без метаданных, id
  уникальны, цвет — `--logo-color`, контраст с `--logo-bg` ≥ 3 в обеих темах сайта);
  иконки — `favicon.svg`, `favicon-32.png`, `apple-touch-icon.png` (180×180) из `favicon.svg`.
- **Пока сайт не открываем** (у владельца нет ИП, заявки принимать нельзя). На joy-rest.ru по
  умолчанию заглушка «скоро» (`deploy/caddy/soon`, её отдаёт `app-prod`), `/api/lead` — 404.
  Сайт включает только владелец: `sudo joyrest site on|off` → `SITE_ENABLED` в
  `/srv/joyrest/settings.env` (без нового релиза). Включает только точное `on` (`isOn`);
  ни слияние PR, ни выкладка, ни перезагрузка, ни CI сайт не включают — это проверяет
  `server/src/siteSwitch.test.ts`. В compose значения по умолчанию — только `off`.
- test.joy-rest.ru (`app-test`) показывает сайт всегда, `noindex` всегда и закрыт паролем:
  `basic_auth` в Caddy. Хэш владельца — файл `/srv/joyrest/caddy/etc/auth/test-site-owner.caddy`
  вне репозитория (пишет `sudo joyrest site-password`: скрытый ввод, bcrypt через
  `caddy hash-password` по stdin, стоимость 10, пароль ≥ 12 символов; хранится только хэш).
  В Caddyfile всегда есть запирающая учётная запись со случайным неизвестным паролем, поэтому
  без хэша владельца сайт закрыт для всех (fail-closed), а Caddy не падает на пустом списке.
- Caddyfile и команды `joyrest` на сервере берутся из основного релиза: изменения в них
  начинают работать только после слияния в `main` и выкладки.
- Сайт в том же образе (`/app/site`), что и платформа, поэтому выкладка, откат и уведомления
  общие: `main` → joy-rest.ru (`app-prod`), ветки `claude/*` → test.joy-rest.ru (`app-test`).
  Приложение выбирает сайт по заголовку Host (`SITE_HOSTS`, `server/src/site.ts`): у сайта
  и платформы разные пространства адресов, пересечений нет.
- Кэш: `css/`, `js/`, `img/`, `fonts/` — год (`immutable`), `index.html` и `robots.txt` —
  `no-cache`. Сжатие — Caddy (`encode zstd gzip`).
- Поисковики: `SITE_INDEXING` в `/srv/joyrest/settings.env`, переключает
  `sudo joyrest site-indexing on|off` — включить можно только при `site on`, `site off`
  сбрасывает индексацию в `off`; по умолчанию `off` — `robots.txt` Disallow и
  `X-Robots-Tag: noindex, nofollow` на всех ответах сайта и заглушки. test.joy-rest.ru закрыт всегда.
  Открывает владелец сам, когда решены юридические вопросы (политика, ФИО, ИНН).
- Заявки (только при `site on`): формы шлют `POST /api/lead` (тот же домен, без CORS; только с адресов сайта)
  — типы `question`, `review`, `lead` (`server/src/lead.ts`). Тело ≤ 8 КБ, проверка полей и
  длины, управляющие символы вырезаются (кроме переводов строк), согласие обязательно,
  скрытое поле-ловушка `website` (бот получает 200, в Telegram ничего не уходит), лимит
  5 заявок за 10 минут на IP и 30 в час на всё приложение (при превышении — 429 и одно
  предупреждение в Telegram). Сообщение в Telegram — простой текст, без `parse_mode`.
  Нет бота — 503 с понятным текстом, сайт работает. Сайт показывает «спасибо» только при
  ответе 200, иначе текст ошибки и ссылку на t.me/JoyRest.
- IP посетителя: Caddy перезаписывает `X-Forwarded-For` (`header_up X-Forwarded-For
  {remote_host}`), приложение верит ему только от адресов частных сетей Docker
  (`trustProxy`, `PRIVATE_NETWORKS` в `server/src/app.ts`). Других путей к приложению нет:
  портов наружу у него нет.
- В журнал из заявок пишем только тип, итог и код ответа — без имён, телефонов и текста.
- Цвета текста на сайте — только токены `site/css/style.css` (`--ink`, `--ink-soft`,
  `--accent-text`, `--green-text`, `--on-accent` для текста на цветных заливках,
  `--btn-*`): белый текст на пастели и пастельный текст на фоне запрещены. Контраст пар в
  светлой и тёмной теме (текст ≥ 4.5, рамки ≥ 3) проверяет `server/src/site.test.ts`.
- Эмблема первого экрана — `joyrest-emblem.svg` под маской (`img/joyrest-emblem-mask.svg`,
  делает сборка) с фирменным градиентом темы: блик раз в 7 с и наклон ±8°, только
  transform/opacity, при «уменьшить движение» — статична; наклон от датчика — только где не
  нужен запрос разрешения (на iPhone не используется).
- Стартовые форматы с молодыми ведущими — «Новые лица» (−25%) и «Первый старт» (−35%):
  карточки в «Пакетах услуг» (тексты согласованы с владельцем, правка только с ним),
  выбор «Ведущий» в калькуляторе (скидка на работу ведущего — последней строкой, после
  остальных скидок), поле «Формат ведущего» в заявке и необязательное `hostLevel`
  (`standard` | `new` | `first`) в `/api/lead` → строка «Ведущий: …» в Telegram.
- Пока нет мероприятий, форма отзыва скрыта: `data-review-form="off"` у `#reviews`
  (вернуть — `on`); тип `review` в `/api/lead` остаётся.

**Правило: токены и ключи — только на сервере.** Токен бота заявок
(`LEAD_TELEGRAM_TOKEN`, `LEAD_TELEGRAM_CHAT_ID`) хранится только в `/srv/joyrest/secrets.env`,
задаётся командой `sudo joyrest lead-bot` (скрытый ввод, проверка, перезапуск приложения).
Ни в коде сайта, ни в репозитории, ни в образе, ни в GitHub Secrets его нет; браузер
никогда не обращается к api.telegram.org. Тест `server/src/secrets.test.ts` ищет строки,
похожие на токен Telegram (`\d{8,10}:AA[\w-]{30,}`), в корне репозитория, `site/`, `src/`,
`server/`, `deploy/`, `docs/`, `scripts/`, `public/`, `.github/` и падает, если нашёл.

## 3. Роли и экраны

Роли пользователей:
- **admin** — владелец агентства: добавляет и отключает ведущих, ведёт общую библиотеку.
- **host** — ведущий: свои игры, копирование шаблонов, запуск сессий.
- **guest** — гость: анонимный вход по коду сессии, без регистрации.

Регистрация ведущих закрыта: аккаунт создаёт только admin в `/admin` (почта + имя).
Аккаунт создаётся через вторичный экземпляр Firebase Auth (`loadSecondaryAuth`), чтобы
админ не разлогинился; временный пароль показывается один раз и нигде не хранится,
ведущий меняет его в студии. Отключение (`active = false`) блокирует вход в студию и пульт,
создание сессий и игр (так же в правилах). Удалить аккаунт Auth без Cloud Functions нельзя,
поэтому ведущих не удаляем, а отключаем.

Библиотеки игр: общую (`scope: "agency"`) правит только admin, ведущие запускают её игры
как есть или копируют в «Мои игры» (`scope: "personal"`, видит только владелец).

Экраны (маршруты):
- `/studio` — студия: вкладки «Библиотека JoyRest», «Мои игры», «История игр» (`?tab=`).
  `/studio/new` — новая игра, `/studio/games/:id` — игра (автосохранение),
  `/studio/launch/:id` — запуск сессии, `/studio/password` — смена пароля.
- `/admin` — управление ведущими (только admin); при входе — автоочистка старых сессий.
- `/results/:id` — итоги прошедшей игры по ссылке, открываются без входа.
- `/host/:code` — пульт ведущего. Можно открыть на нескольких устройствах сразу.
- `/screen/:code` — экран зала (ноутбук, телевизор, проектор, браузер Smart TV).
- `/play/:code` и `/j` — вход гостя по QR или по коду и телефон игрока.
- `/brand` — служебная витрина фирменного стиля: палитра, шрифты, кнопки, логотипы.

Любое устройство может стать любым экраном, если открыть нужный адрес с кодом сессии.

## 4. Режимы проведения

Ведущий выбирает режим при запуске сессии:
1. **Ноутбук + экран.** Ноутбук показывает экран зала; управление с ноутбука или с
   телефона как пульта (рекомендуемый вариант: ведущий свободно ходит по залу).
2. **Телефон-пульт + отдельный экран.** Экран зала открыт на любом устройстве.
3. **Без экрана.** Только телефон ведущего. Вопросы и варианты показываются прямо на
   телефонах гостей, ведущий читает вслух.

Режим участников:
- **solo** — каждый гость играет сам.
- **teams** — команды; к команде можно подключить несколько телефонов, ответ
  отправляет капитан, остальные видят вопрос.

Вся игровая логика работает с абстракцией «участник» (игрок или команда) и не зависит
от режима.

## 5. Модель данных (Firestore)

```
users/{uid}                 role, name, active, email, createdAt
games/{gameId}              scope: "agency" | "personal", ownerId, title,
                            mechanic, themeId, ageRating: "0+" | "12+" | "18+",
                            playMode: "solo" | "teams" (по умолчанию при запуске),
                            content, createdAt, updatedAt (serverTimestamp)
games/{gameId}/media/{mediaId}         bytes (WebP/JPEG), mime, width, height,
games/{gameId}/media/{mediaId}-small   variant: "full" | "small", createdAt
sessions/{sessionId}        code, hostId, gameId, gameTitle, mechanic, gameSnapshot, themeId,
                            playMode: "solo" | "teams",
                            screenMode: "laptop" | "remote" | "none",
                            state { phase: "lobby" | "playing" | "finished",
                                    step, startedAt, revealed,
                                    stage: "ready" | "question" | "reveal" | "board",
                                    timeLimit, answered, result },
                            leaderboard { [pid]: { name, kind, score, colorIndex?,
                                                   last?, captainUid? } },
                            createdAt (serverTimestamp)
sessions/{id}/participants/{pid}   name, kind: "player" | "team", teamId, captainUid,
                                   joinedAt (serverTimestamp), seenAt? (сигнал капитана)
sessions/{id}/answers/{step_pid}   step, pid, uid, value, submittedAt (serverTimestamp)
clock/{uid}                 t (serverTimestamp) — смещение часов экрана зала и пульта
results/{sessionId}         hostId, code, gameTitle, mechanic, themeId, playMode,
                            playedAt, participantsCount,
                            board [{ name, score, colorIndex? }] (по убыванию очков),
                            savedAt (serverTimestamp)
```

Уточнения к модели (этап 1):
- `code` — 6 цифр, уникален среди незавершённых сессий. Сессия ищется запросом
  `where code == X` и `where state.phase in ["lobby", "playing"]` с лимитом 5: правила
  пропускают поиск по коду только для незавершённых сессий. После «Завершить игру» сессию по
  коду не найти; ведущий находит свою по `code` + `hostId`, admin видит все. Телефон гостя и
  экран зала запоминают id сессии (localStorage) и после завершения открывают её по id
  (`get` разрешён всем вошедшим), поэтому гость видит финал своей игры.
- Телефон гостя — документ участника с `pid = uid`, поэтому повторный вход не создаёт
  дубль. В режиме teams команда — отдельный документ `kind: "team"` с автоматическим id,
  её создатель — капитан (`captainUid`); телефоны участников команды ссылаются на неё
  через `teamId`. В `leaderboard` попадают только игроки (solo) или только команды (teams).
- Экран зала не слушает участников: пульт ведущего переносит новых участников в
  `leaderboard` с нулём очков, и экран видит их через документ сессии.
- `colorIndex` есть только у команд: пульт выдаёт следующий по порядку цвет команды
  при добавлении в `leaderboard`, и цвет больше не меняется.
- Владелец агентства определяется по UID, зашитому в `firestore.rules` и
  `src/data/config.ts`; его профиль `users/{uid}` создаётся при первом входе. Его нельзя
  отключить, понизить или удалить.

Уточнения к модели (этап 2):
- История игр — коллекция `results`: компактные итоги без ответов и участников. Пульт пишет
  их одной пачкой вместе с `state.phase = "finished"` при завершении игры. `participantsCount` —
  число телефонов гостей. Итоги открываются по ссылке без входа (`allow get: if true`: там
  только названия и очки), списком — только своему ведущему и admin.
- Автоочистка без Cloud Functions: при каждом входе admin в `/admin` удаляются сессии старше
  30 дней (`src/core/retention.ts`) вместе с участниками и ответами — до 100 сессий за вход.
  Если у сессии с участниками ещё нет итогов (игру не завершили), admin сначала сохраняет их.
- Запросы без составных индексов: списки игр, сессий и итогов фильтруются только по
  равенству (или одному диапазону `createdAt`) и сортируются в браузере.

Уточнения к модели (этап 3, конструктор):
- Картинки не хранятся в документе игры и не копируются в `gameSnapshot`: в вопросе только
  `imageId`. Картинка сжимается на устройстве ведущего (`src/components/media/compressImage.ts`):
  полная — WebP до 1280 px по длинной стороне и ~150 КБ (Safari на iPhone не кодирует WebP —
  тогда JPEG), уменьшенная — до 480 px, ~35 КБ. Оба варианта пишутся одной пачкой в
  `games/{id}/media` (`MediaRepository`); правила пропускают не больше 400 КБ на документ.
- Картинку по id читает любой вошедший (`get`): экран зала и телефоны гостей входят анонимно.
  Списком — только тот, кто правит игру. Перезаписать нельзя, только создать или удалить.
- Экран зала загружает картинки сам и заранее (текущий и следующий вопрос). Телефоны гостей
  картинки не грузят, кроме режима «без экрана» — там уменьшенная версия.
- Копия и дубль игры (`gamesRepo.copy`) копируют картинки с теми же id: первая пачка создаёт
  игру вместе с картинками (правила проверяют права через `getAfter`). Удаление игры удаляет
  все её картинки, саму игру — последней пачкой. Картинку, загруженную и тут же заменённую
  или убранную в конструкторе, удаляем сразу; старые остаются до удаления игры, потому что
  на них может ссылаться уже запущенная сессия.

Уточнения к модели (этап 4, квиз в игре):
- Шаг игры проходит этапы `state.stage`: `ready` («Вопрос 2 из 8», ведущий ещё не показал) →
  `question` (таймер: `startedAt` ставит сервер, `timeLimit` — секунды) → `reveal` (правильный
  ответ, `revealed = true`) → `board` (таблица) → следующий шаг. «Назад» возвращает на этап:
  с `reveal` очки шага снимаются (`last`), с `question` ответы шага удаляются.
- Ответ принимается, только пока `stage == "question"` и не вышло время (`request.time ≤
  startedAt + timeLimit + 3 с` в правилах — запас на сеть). То же в `permissions.canSubmitAnswer`.
- `state.answered` — счётчик ответов для экрана, пульт пишет его не чаще раза в 2 секунды.
  `state.result` — итоги шага от механики (квиз: распределение по вариантам, сколько верно,
  засчитанные ведущим открытые ответы `accepted`).
- `leaderboard[pid].last` — очки за последний показанный ответ («+100» на экране и телефоне).
  Места при равных очках общие (10, 10, 7 → 1, 1, 3) — `rankedLeaderboard`.
- Одинаковые имена: пульт вносит в таблицу «Аня», «Аня 2» (`uniqueName`), документ участника
  не трогает. Ручные правки пульта: ± очки, переименовать, убрать участника.
- Команды: капитан известен телефонам из `leaderboard[teamId].captainUid`. Телефон капитана раз
  в 30 с пишет `seenAt`; если сигнала нет 90 с (или телефона капитана нет), пульт делает
  капитаном следующего по времени входа участника команды (`captainChanges`), ведущий может
  назначить капитана сам.
- Телефон запоминает свой ответ (localStorage); после перезагрузки посреди шага и участник
  команды при показе ответа читают ответ по id (`answersRepo.getOwn`): правила пускают `get`
  своего ответа и ответа своей команды, списком ответы видит только пульт.
- Часы: экран зала и пульт один раз пишут `clock/{uid}` с serverTimestamp и читают его, чтобы
  таймер совпадал с сервером. Телефоны идут по своим часам (экономия операций).
- «Репетиция» (`/studio/rehearsal/:id`) — тот же пульт и экран зала на сессии в памяти
  (`core/session.applyChange`), без гостей и без записей в базу.
- Демо-квиз (8 вопросов, `src/mechanics/quiz/demo.ts`) admin добавляет в «Библиотеку JoyRest»
  кнопкой на вкладке библиотеки (`demoGames` в реестре).

Правила экономии лимитов:
- Гости и экран зала слушают **только документ сессии**. Таблица лидеров хранится в нём.
- Ответы слушает только пульт ведущего.
- При запуске сессии игра копируется в `gameSnapshot`: правка игры в конструкторе не
  ломает идущую сессию.
- Ответ гостя пишется одним документом с детерминированным id `step_pid`, поэтому
  повторное нажатие не создаёт дубль.

Подсчёт очков выполняет пульт ведущего (Cloud Functions на бесплатном тарифе нет).
Правила безопасности разрешают менять `state` и `leaderboard` только владельцу сессии.
Удалять сессии может владелец и admin (автоочистка).

Честность вопросов на скорость: время ответа = `submittedAt − state.startedAt`, оба
значения ставит сервер (`serverTimestamp`). Часам телефонов не доверяем.

## 6. Механики как модули

Каждая механика — отдельная папка `src/mechanics/<id>/` с единым интерфейсом:

```ts
interface Mechanic<Content, Answer> {
  id: string;
  title: string;
  supports: { solo: boolean; teams: boolean; noScreen: boolean };
  Editor: Component;        // конструктор
  ScreenView: Component;    // экран зала
  PlayerView: Component;    // телефон гостя
  HostControls: Component;  // пульт
  create(): Content;            // содержимое новой игры
  parse(raw): Content;          // данные из базы → формат механики, без исключений
  mediaIds(content): string[];  // картинки игры (копируются вместе с ней)
  steps(content): Step[];   // последовательность шагов игры
  score(step, answers, { state }): ScoreDelta[]; // state: startedAt, timeLimit, result
  validate(content): ValidationError[]; // path "questions/<id>/<поле>" + понятная подсказка
}
```

`HostControls` получает ответы на шаг, участников и `SessionControl` (`apply` — одна запись
состояния и таблицы, `clearAnswers`, `requestFinish`): на настоящей сессии он пишет в базу, в
репетиции — в память. `PlayerView` получает `pid` (кто получает очки), роль телефона
(`player`/`captain`/`member`) и свой ответ. Ход квиза — чистые функции `quiz/flow.ts`.
Очки за скорость: самый быстрый верный ответ — максимум, ответ в последнюю секунду — половина.

Ядро и экраны работают с механикой из реестра как с `AnyMechanic` (содержимое `unknown`)
и всегда сначала вызывают `parse`. Игру с ошибками `validate()` запустить нельзя: кнопка
«Запустить» неактивна, экран запуска показывает, что исправить. Конструктор механики —
отдельный чанк (`lazy`), телефону гостя он не нужен.

Квиз (`src/mechanics/quiz/`): вопросы `choice` (2–6 вариантов, один верный), `open` (несколько
верных ответов, сравнение без регистра, ё/е, пробелов и пунктуации — `normalize.ts`),
`speed` (варианты, очки по времени); у каждого время, очки и картинка. Импорт списком
(`importText.ts`): вопрос с новой строки, варианты с «-», верный с «*», открытый ответ
«= ответ1 | ответ2». Виды экрана зала размечены в единицах контейнера (`cqw/cqh`), поэтому
предпросмотр в студии совпадает с телевизором.

Новая механика подключается регистрацией в `src/mechanics/registry.ts` и не требует
изменений в ядре. Ядро ничего не знает о конкретных играх.

Очередь механик:
1. Квиз: варианты ответа, открытый ответ, на скорость, вопрос с картинкой и аудио.
2. «Угадай мелодию» и музыкальное лото.
3. Тайные роли: Мафия, Бункер, Шпион.
4. Игровые поля: Just Dance Battle, ходилки «Алкогольные / Сладкие приключения».
5. Голосования: Битва тостов, Замри.

## 7. Музыка и медиа

- Основной режим: аудиофайлы выбираются с устройства ведущего и хранятся локально
  (IndexedDB) на том устройстве, где открыт экран зала. На сервер не загружаются.
- В игре хранится только ссылка на трек: имя файла, начало фрагмента, длительность.
- Если файла нет на устройстве, экран зала показывает понятное сообщение и предлагает
  выбрать файл заново.
- Запасной режим «свой плеер»: платформа показывает только кнопки и считает очки.
- Звук играет только на экране зала, никогда на телефонах гостей.

## 8. Темы оформления

Тема — это данные, а не код: палитра, шрифты, фон, звуки, анимации.

```
themes/<id>.ts   id, title, kind: "brand" | "seasonal" | "occasion",
                 tokens { colors, fonts, radius, background }, sounds, ageRating
```

- Базовая тема — фирменный стиль JoyRest.
- Сезонные: Новый год, 23 февраля / 8 марта, лето, Хэллоуин и т.д.

Сетка и поля:
- отступы кратны 8px (8, 16, 24, 32); внутренний отступ карточек 24px, промежутки 16px;
- поля страницы на телефоне 20px, учитываются `safe-area` сверху, снизу и по бокам;
- снизу у страницы запас 88px (`--bottom-clearance`): плавающая панель Netlify на тестовых
  ссылках и уведомления не перекрывают контент;
- заголовки с `text-wrap: balance`, длинные строки (адрес, код) — в одну строку с обрезкой.

Вкладки — компонент `Tabs`: тихие кнопки, у выбранной полоса градиента снизу, стрелки
переключают. Дополнительные действия карточки — кнопка «⋯» (`ActionMenu`, тот же список,
что меню ☰ в шапке). Необратимые действия («Удалить игру», «Отключить») — только через
`ConfirmDialog`. Подробности карточки (механика, тема, число вопросов, дата) — плашки `.meta`.

Загрузка: вместо текста «Загружаем…» — каркас экрана (`src/components/Skeleton.tsx`)
через `Pending`. Медленная сеть — не ошибка: загрузка не прерывается и сама повторяется после
сетевых сбоев с паузой 2, 4, 8, дальше каждые 10 секунд (`withRetry` в `src/data/retry.ts`).
Через 8 секунд под каркасом — плашка «Подключаемся… интернет медленный, подождите» с
индикатором и маленькой кнопкой «Обновить страницу», через 30 секунд — «Всё ещё подключаемся —
проверьте связь или Wi‑Fi». Данные пришли — экран открывается сам. Ошибкой с остановкой
(`LoadFailed`) показываются только настоящие ошибки: не найдено, нет доступа (`isPermanentError`).
Обрыв связи во время работы — тонкая полоса сверху «Нет связи — переподключаемся…»
(`ConnectionBanner`, источник — `connection` из слоя данных), после восстановления — короткое
«Связь восстановлена»; экран не закрывается, подписки Firestore догоняют данные сами.
Уведомления о действиях — `Toast` («Ссылка скопирована»).

Скорость: Firebase грузится динамически (`src/data/firebase.ts`) через обёртки
`src/data/sdk/*.ts` с именованным реэкспортом — новую функцию SDK добавляйте туда,
иначе пропадёт tree-shaking. Экраны — отдельные чанки (`lazy` в `App.tsx`); главная и
`/j` не грузят Firebase.

Логотип — готовые файлы в `public/brand/` (не перерисовывать):
- `joyrest-logo.svg` — полный логотип: монограмма «J✦R», JOYREST, EVENTS & EXPERIENCES;
- `joyrest-monogram.svg` — монограмма;
- `joyrest-emblem.svg` — эмблема с аркой для заставки;
- `favicon.svg` — иконка сайта.

Логотипы закрашены `currentColor` и встраиваются в страницу компонентом
`src/components/Logo.tsx` (импорт `?inline-svg`, метаданные вырезаются при сборке). Цвет —
`--color-logo` из темы, id внутри clipPath делаются уникальными для каждого экземпляра.
Заливки для будущих тем: золотая #F3DFAE → #C9A15F → #E9CF93 (свадьбы), праздничная
#7FB3FF → #B79CFF → #F59AD7 (вечеринки) — `tone="gold"` и `tone="festive"`.

Размещение: эмблема крупно на заставке экрана зала, пока гости подключаются; монограмма
в углу экрана зала во время игры и после неё; полный логотип над формой входа гостя;
монограмма в шапке пульта и студии; монограмма в центре QR-кода.

## 9. Надёжность — обязательные требования

- Гость, у которого погас экран или пропал интернет, возвращается в игру автоматически
  и видит текущий шаг.
- Если ведущий закрыл вкладку, игра продолжается с того же места после открытия пульта.
- Слабый интернет на площадке — норма: на телефон гостя передаём минимум данных,
  тяжёлые медиа только на экране зала.
- Нагрузочный симулятор `scripts/simulate.ts`: запускает N виртуальных гостей
  (до 500) против тестовой сессии. Прогонять перед каждым релизом механики:
  `GUESTS=500 npm run simulate` (`TEAMS=1` — режим команд). Демо-квиз, 8 вопросов:
  50 гостей — ~4,4 тыс. чтений и ~510 записей на игру; 500 гостей — ~34 тыс. чтений и
  ~4,5 тыс. записей (лимит Spark в сутки: 50 тыс. чтений, 20 тыс. записей). Основные
  статьи: гости слушают документ сессии (~45–60 обновлений за игру) и проверки правил
  при ответе (2 чтения на ответ).
- Экран зала и телефон гостя не гаснут во время игры (Wake Lock, `useWakeLock`).
- Конструктор сохраняет изменения автоматически, ни одна правка не теряется
  (`src/components/useAutosave.ts`: пачка правок через 0,7 с уходит сразу, не дожидаясь
  ответа на предыдущую, — запись ложится в очередь локального кэша Firestore и переживает
  обрыв связи и закрытие вкладки; после отказа сервера — повтор со свежими значениями;
  досылка при сворачивании вкладки). Индикатор: «Сохранено», «Сохраняется…», «Нет связи»
  (браузер офлайн или сервер молчит дольше 5 с).

## 10. Правила разработки

- Маленькие задачи, понятные коммиты на русском языке.
- Каждая механика покрыта тестами логики `steps` и `score`.
- Правила безопасности Firestore лежат в `firestore.rules` и покрыты тестами.
  После изменения правил напиши владельцу пошагово, как вставить их в консоль Firebase.
- Секреты в репозиторий не кладём. Конфигурация веб-приложения Firebase не секретна;
  ключи сервисного аккаунта запрещены. Токены ботов и API — только на сервере
  (`/srv/joyrest/secrets.env`, раздел «Сайт агентства»).
- Интерфейс: сначала мобильная версия для гостя, крупные кнопки, видимый фокус,
  уважение к настройке «уменьшить движение».
- Тексты интерфейса простые и конкретные: кнопка называет действие («Начать игру»,
  «Показать ответ»).
- После каждой завершённой задачи кратко сообщай, что проверить по тестовой ссылке.
