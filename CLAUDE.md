# JoyRest Games — технический паспорт проекта

Этот файл читается в начале каждой сессии Claude Code. Он фиксирует архитектуру и правила.
Любое изменение архитектуры сначала вносится сюда, потом в код.

## 1. Что мы делаем

Интерактивная веб-платформа для ведущих агентства JoyRest (Москва): квизы и игры на
свадьбах, корпоративах, днях рождения. Гости играют со своих телефонов, вопросы
показываются на большом экране, ведущий управляет игрой с пульта.

- Типичное мероприятие: 20–50 гостей. Расчётный максимум: 500 гостей в одной сессии.
- Несколько ведущих работают одновременно, каждый в своих сессиях.
- Язык интерфейса: русский.
- Владелец проекта работает только с телефона: проверка идёт по тестовым ссылкам
  хостинга, а не локально. Всё, что нужно сделать руками, описывай пошагово для
  мобильного браузера.

## 2. Стек

- Vite + React + TypeScript (strict, без `any`).
- Firebase: Authentication (почта/пароль для ведущих, анонимный вход для гостей),
  Firestore (данные и синхронизация в реальном времени). Firestore работает с
  `persistentLocalCache` и `experimentalAutoDetectLongPolling` (медленные мобильные сети).
- Бесплатный тариф Spark: Cloud Functions и Storage не используем.
- Хостинг: Netlify с автопубликацией из GitHub (`netlify.toml`). Каждая ветка получает
  свою тестовую ссылку.
- Тесты: Vitest для логики, эмулятор Firebase для правил безопасности.

### Слой данных и возможный переезд (обязательное правило)

Возможен переезд с Firebase на свой сервер (Node.js + WebSocket на VPS в России). Поэтому:

- Всё, что связано с Firebase (Auth, Firestore, правила), — **только внутри `src/data/`**.
  Экраны, компоненты, механики и `src/core/` не импортируют `firebase/*` и внутренние
  модули слоя данных.
- Экраны и механики работают через интерфейсы `src/data/contracts.ts`: `AuthService`,
  `UsersRepository`, `GamesRepository`, `SessionsRepository`, `ParticipantsRepository`,
  `AnswersRepository`, `ResultsRepository`, `MediaRepository`, `ClockService`. Экземпляры (`authService`, `gamesRepo`,
  `sessionsRepo`, …) и типы берутся только из `src/data/index.ts`. При переезде пишется
  новая реализация тех же интерфейсов, остальной код не меняется.
- Логика прав («кто что может») продублирована в `src/data/permissions.ts` обычными
  функциями без Firebase и покрыта тестами (`permissions.test.ts`). Интерфейс решает по ним,
  что показывать; будущий сервер проверяет по ним запросы. `firestore.rules` и
  `permissions.ts` меняются только вместе, вместе с обоими наборами тестов.
- Тест `src/data/boundary.test.ts` проверяет, что вне `src/data/` нет импортов Firebase и
  внутренних модулей слоя данных (единственное исключение — загрузчик SDK в `main.tsx`).

### Переезд на свой сервер (идёт сейчас)

Платформа переезжает с Firebase и Netlify на свой сервер в России (VPS Beget, Ubuntu 24.04,
2 vCPU / 2 ГБ, 217.114.13.92, домен games.joy-rest.ru). Персональные данные (имена гостей,
почты ведущих), логи и бэкапы хранятся только в России. Пока идёт переезд, Firebase-версия
работает как раньше; после переключения Netlify перенаправляет на games.joy-rest.ru, данные
Firebase удаляются, Firebase-код удаляется отдельным PR.

Архитектура сервера:
- Docker Compose (`deploy/compose.yml`), проект `joyrest`: `caddy` (HTTPS для games.joy-rest.ru
  и сайта агентства joy-rest.ru, www → joy-rest.ru) → `app-prod` (Node.js 22 + TypeScript,
  Fastify: платформа, сайт агентства по Host, `/health`, `/api/lead`, дальше `/api` и `/ws`) → `postgres` (PostgreSQL 17, одна на
  основное и тестовое окружение, разные базы). У всех контейнеров `mem_limit`.
- Наружу публикует порты только `caddy` (80, 443, 443/udp). Docker обходит ufw, поэтому
  других `ports:` в compose быть не должно (проверяет CI). База — во внутренней сети.
- Основная и тестовая версии разделены: сети `web`/`db` — Caddy, app-prod, postgres; `web-test`/`db-test`
  — Caddy, app-test, postgres (app-test до app-prod не достучится). Приложения ходят в базу своими
  ролями без суперправ — `joyrest_app_prod` только в `joyrest_prod`, `joyrest_app_test` только в
  `joyrest_test` (`sudo joyrest db-roles`, один раз из Termius; пароли — `PROD_DB_*`/`TEST_DB_*` в
  `secrets.env`; до этого — прежний `joyrest`). Права повторяются при каждой выкладке и после
  восстановления (`db_role_grants`). Миграции, дампы и восстановление — по-прежнему `joyrest`.
  Проверяет `server/src/dbRoles.test.ts`.
- Код сервера — `server/`, собирается esbuild в один файл (`npm run build:server`).
  Сервер переиспользует `src/data/permissions.ts` и типы `src/data/types.ts`.
- Всё собирается в GitHub Actions (`.github/workflows/build.yml`): тесты → образ
  `ghcr.io/joonde/joyrest-app:sha-<коммит>` (сайт + сервер + `deploy/`). Сервер только
  скачивает образы из GHCR и ничего не собирает (2 ГБ памяти). Docker Hub с российских IP
  ограничен: базовые образы (`caddy`, `postgres`) копируются в `ghcr.io/joonde/joyrest-mirror/`
  (`mirror-images.yml`, раз в неделю), compose ссылается только на GHCR.
- На сервере: `/srv/joyrest/` — `secrets.env` (только на сервере), `releases/<коммит>/`
  (папка `deploy/` из образа), `current` → текущий релиз, `postgres/`, `caddy/`, `backups/`.
  Управление — команда `joyrest` (`deploy/bin/joyrest`), инструкции владельцу — `RUNBOOK.md`.
- Пользователи сервера: владелец (sudo, вход по ключу из Termius), `deploy` — без sudo и
  консоли, ключ GitHub Actions привязан к привратнику `deploy/bin/joyrest-gate`: он пропускает
  только `ping`, `status`, `deploy <40 hex>`, `deploy-test <40 hex>` (тестовый ключ — без `deploy`) и кладёт запрос
  в очередь `/srv/joyrest/deploy/queue/`; выкладывает служба root (`deploy/systemd/`).
- Выкладка (`joyrest deploy`, `.github/workflows/build.yml`, задача `deploy`): main →
  games.joy-rest.ru, ветки `claude/*` → test.games.joy-rest.ru (`app-test`, база
  `joyrest_test`, `mem_limit` 256m). Шаги: блокировка → проверка игры → образ по отпечатку →
  дамп базы (`backups/predeploy`, 5 последних) → миграции (`server/migrations`, только
  добавляющие) → переключение → `/health` с новой версией → иначе откат на прошлую.
  Тестовое окружение общее (сайт и платформа): коммит ветки `claude/*` с `[no-test]` в
  сообщении на test не выкладывается (задача `deploy` пропускается, сборка, тесты и образ — как
  обычно; на `main` пометка не действует). Ставьте `[no-test]`, если test для проверки не нужен
  (например, команды `joyrest` и службы — они ставятся только из основного релиза). Решает
  сообщение последнего коммита в push.
  Основная версия — только по SSH из `main`: задача `deploy` идёт в окружении GitHub `production`
  (правило «только main»), ключ `DEPLOY_SSH_KEY` лежит только там. Ветки — своим ключом
  `DEPLOY_SSH_KEY_TEST` (`sudo joyrest deploy-key test|prod` — новый ключ, показывается один раз), привратник пускает его только на `ping`,
  `status`, `deploy-test` (`joyrest-gate test`). `force` с ключей не принимается — только из Termius.
  Запасной путь — тег `test-release` в GHCR, который сервер проверяет каждые 2 минуты
  (`joyrest-update.timer`, токен только `read:packages`) — только для test; тег `release` больше не
  ставится и не читается (его могла поставить любая ветка). Проверяет `server/src/deployGuard.test.ts`. Итог
  Actions проверяет по HTTPS `/health` и пишет в Telegram. Включается переменной
  репозитория `DEPLOY_ENABLED=true`: задача «Переключатель выкладки» (`switch`) сравнивает
  её без учёта регистра, `\r\n`, пробелов по краям и невидимых символов (вставка с телефона)
  и при выключенной выкладке показывает в логе, что видит. Секреты Telegram и SSH тоже
  очищаются от пробелов и `\r\n`; причина неудачной отправки в Telegram пишется в лог.
- Блокировка выкладки во время игры: основная версия не выкладывается, если есть сессия с
  `phase in ('lobby', 'playing')` и `updated_at` за последние 30 минут, идущая игра (`playing`) с
  действием пульта за 3 часа (`PLAYING_HOURS` — перерыв на свадьбе); брошенная игра дольше не держит. Если проверить не
  удалось (база не отвечает) — тоже считается, что игра идёт: статус `blocked`, таймер
  повторит. `force` — только вручную из Termius (`sudo joyrest deploy <коммит> force`); CI
  `force` не отправляет, тег `test-release` ставит только при `DEPLOY_ENABLED`.
- **Миграции только обратно совместимы (expand/contract).** Они выполняются до переключения
  версии, а откат возвращает прошлый код, но не схему: новая схема обязана работать со
  старым кодом. Можно: новые таблицы, колонки с `DEFAULT` или без `NOT NULL`, индексы.
  Нельзя в обычной миграции: `DROP`, `RENAME`, смена типа, `SET NOT NULL`, `NOT NULL` без
  `DEFAULT`, `TRUNCATE`, `DELETE`. Удаление — отдельной contract-миграцией (первая строка
  `-- contract: <что и с какого релиза не используется>`), не раньше чем через релиз после
  того, как код перестал это использовать. Переименование = новая колонка + код пишет в обе
  + contract-миграция. Проверяет тест `server/src/migrationRules.test.ts`.
  Поэтому таблица `sessions` на сервере обязана иметь `phase` и `updated_at` (обновляется
  при каждом действии пульта).
  После проверки выкладки: `PermitRootLogin no`, `PasswordAuthentication no` (`lock-ssh.sh`).
- Первичная настройка: `deploy/setup/check.sh` (проверка связи, ничего не меняет) →
  `deploy/setup/install.sh` (система, ufw, fail2ban, автообновления, Docker, ротация логов
  Docker 10m×3 и journald 200 МБ/14 дней, запуск). Секреты показываются один раз.
- Резервные копии (`joyrest backup*`, `restore`, `deploy/systemd/joyrest-backup.*`): каждую ночь
  в 04:40 дамп `joyrest_prod` (проверенный `pg_restore --list`) → диск (`backups/daily`, 3) и restic
  → Beget S3 (зашифровано). Сроки: 7 ежедневных, 4 еженедельных, 3 ежемесячных (+ до недели до
  `prune`). Раз в неделю `prune`, `check --read-data-subset=10%` и итог в Telegram, раз в месяц —
  восстановление во временную базу; `prune` и проверки при игре (правило 30 минут) — на следующую
  ночь. Доступы — только `/srv/joyrest/backup.env` (пишет `sudo joyrest backup-setup`, пароль
  restic показывается один раз), `secrets.env` в копию не входит. Сообщения сервера — служебный
  бот (`sudo joyrest notify-bot` → `NOTIFY_TELEGRAM_*` в `secrets.env`, приложения его не видят).
  Основная база восстанавливается только из Termius с подтверждением, прежняя остаётся
  `joyrest_prod_before_restore`. Версионирования и object lock у Beget S3 нет. Проверяет
  `server/src/backup.test.ts`.
- Минуты Actions (закрытый репозиторий, 2000 в месяц) — только на сборку и выкладку
  (исключение — нагрузочная проверка «Нагрузка», только вручную, ~5 минут).
  Внешний мониторинг «сайт недоступен» — UptimeRobot, не cron в Actions.

Этапы переезда (PR): 1 — инфраструктура; 2 — выкладка (SSH + сервер сам забирает релиз,
откат, тестовое окружение test.games.joy-rest.ru, блокировка выкладки при игре с активностью
за 30 минут); 3–4 — сервер (вход argon2 + httpOnly-cookie, токены устройств гостей с мягким
лимитом выдачи по IP, REST, WebSocket, права на сервере); 5 — клиент `src/data/server/` и
офлайн-очередь; 6 — бэкапы (restic → Beget S3, пароль restic и ключи S3 владелец хранит у себя)
и мониторинг (Telegram, UptimeRobot); 7 — нагрузка (не запускается при активной игре);
9 — переключение; 10 — удаление Firebase.

### Платформа на своём сервере (этапы 3–5, идёт сейчас)

Цель: всё на своём сервере — ведущие, игры, картинки, история. Firebase остаётся только как
страховка для отката на время переезда и удаляется в PR 10.

- **Переключатель.** Образ один на оба окружения, поэтому реализация слоя данных выбирается
  при запуске: `DATA_BACKEND` в compose. app-test — всегда `server`, app-prod —
  `${DATA_BACKEND:-firebase}` из `settings.env`. Переключает только владелец:
  `sudo joyrest data server` (этап 9; отказ, если в основной базе нет владельца с паролем —
  сначала `sudo joyrest admin-password`; во время игры — только с `force`), откат —
  `sudo joyrest data firebase`. Выкладка, CI и привратник `DATA_BACKEND` не трогают
  (`server/src/platform.test.ts`). Основная версия переключена на свой сервер 7 октября 2026.
  Netlify (`netlify.toml`) перенаправляет любой адрес на games.joy-rest.ru с тем же путём (302;
  301 — с удалением Firebase).
  Сервер вставляет в `index.html` метку `<meta name="joyrest-data" content="server|firebase">`
  (`withDataBackend`, `server/src/app.ts`); свой сервер — только точное `server`, иначе Firebase.
  `src/data/index.ts` по метке берёт реализацию; сборка Netlify метки не имеет — Firebase.
- **Порядок PR:** 3.0 подготовка (метка, compose, папки медиа, `joyrest admin-password`) →
  3.1 вход и ведущие → 3.2 игры и картинки → 4.1 игра в реальном времени (сессии, гости,
  WebSocket) → 4.2 история и автоочистка → 5 перенос из Firebase → 7 нагрузка → 9 переключение
  prod → 10 удаление Firebase. Каждый PR проверяется на test и сливается: prod на Firebase, пока
  его не переключили, миграции только добавляющие.
- **Экраны и механики не меняются:** `src/data/server/` — вторая реализация интерфейсов
  `contracts.ts`. Исключения — `/admin`: «Новый временный пароль» и перенос из Firebase.
- **Вход ведущих (PR 3.1):** пароль — scrypt из встроенного `node:crypto` (N = 2^15, r = 8, p = 1,
  соль 16 байт; формат `scrypt$15$8$1$<соль>$<хэш>`, `server/src/password.ts`) — без сторонних пакетов
  и нативных модулей. Каждый хэш — ~32 МБ, поэтому одновременно считается не больше 2
  (`SCRYPT_PARALLEL`, очередь `Slots`, FIFO), остальные проверки ждут. Cookie `__Host-jr_s` (httpOnly, Secure, SameSite=Lax, 30 дней, продлевается
  не чаще раза в сутки), в базе `auth_sessions` — sha256 от неё. Попытки входа: 10 за 15 минут на
  IP + почту и 30 на IP (429). Неизвестная почта проверяется так же долго, ошибка одна —
  `auth/invalid-credential`. Отключение ведущего, новый временный пароль и смена пароля закрывают
  его другие сеансы. Владелец агентства на своём сервере — аккаунт с id `ADMIN_UID` (тот же, что в
  Firebase, — для переноса); пароль — `sudo joyrest admin-password [test]` (скрытый ввод, ≥ 12
  символов; почта и пароль — строками через stdin в `server/admin-password.js`). Ведущим пароль
  выдаёт admin в `/admin` («Новый временный пароль» в меню «⋯», показывается один раз;
  `users.must_change_password` → `HostGate` ведёт на `/studio/password`, пока ведущий не задаст свой);
  так же после переноса из Firebase (пароли Firebase не переносятся) — для любого числа ведущих.
  Право — `permissions.canResetHostPassword` (только свой сервер, в `firestore.rules` его нет).
- **API входа (`server/src/auth.ts`):** `GET /api/auth/me`, `POST /api/auth/login|logout|password`,
  `GET|POST /api/users`, `POST /api/users/:id/active|password`. Ответы `no-store`, тело ≤ 4 КБ.
  Изменения — только с заголовком `X-JoyRest: 1` и `Origin` своего адреса (иначе 403); на адресах
  сайта агентства API нет (404). Ошибки — `{ "error": "<код>" }` с кодами как у Firebase
  (`auth/invalid-credential`, `auth/user-disabled`, `auth/too-many-requests`,
  `auth/email-already-in-use`, `auth/weak-password`, `auth/wrong-password`, `unauthenticated`,
  `permission-denied`, `not-found`, `invalid-argument`): тексты (`src/data/authErrors.ts`) и повторы
  (`retry.ts`) общие для обеих реализаций. В журнал — только действие и итог, без почты и паролей.
- **Выбор реализации в браузере:** `src/data/backend.ts` читает метку, `src/data/active.ts` выбирает
  экземпляры, `index.ts` и `hooks.ts` берут их только оттуда. На своём сервере Firebase SDK не
  скачивается (`preloadData` ничего не делает). `src/data/server/`: `api.ts` (fetch, `ApiError` с
  кодом; сбой сети и 5xx — `unavailable`, повторяется), `auth.ts`, `users.ts`; ещё не перенесённое
  (игры, картинки, сессии, гости, ответы, история) до своих PR отвечает `unimplemented`
  (`unavailable.ts`) — на test эти экраны показывают ошибку, а не крутят загрузку.
- **Гости и экран зала:** токен устройства в cookie `__Host-jr_d` (180 дней), `uid` устройства —
  его `AuthUser.uid`. Мягкий лимит выдачи по IP (весь зал за одним Wi‑Fi): до 600 новых в час —
  сразу, дальше задержка 1–3 с, потолок 3000 в час.
- **API:** REST `/api/...` по методам `contracts.ts`; подписки как в Firestore (документ сессии — все,
  участники и ответы — только ведущий сессии) — **поток событий сервера (Server-Sent Events)**
  `GET /api/stream/session/:id`, `/participants/:id`, `/answers/:id/:step`: снимок при подписке, дальше
  только изменения (`state` целиком, изменённые записи таблицы, `version`). Решение PR 4.1 вместо
  WebSocket: подпискам нужен только поток от сервера к браузеру, а записи и так идут REST; поток —
  обычный HTTP (Caddy, HTTP/2, мобильные прокси), браузер сам переподключается и получает свежий
  снимок, пакеты не нужны (`server/src/live.ts`, рассылка — `Hub` в памяти одного процесса app).
  Сервер шлёт «я жив» раз в 25 с, заголовки `no-store, no-transform`, `X-Accel-Buffering: no`. Изменения — проверка
  `Origin` и заголовок `X-JoyRest`. Права — функции `src/data/permissions.ts`, время ответа и
  `startedAt` ставит сервер (`canSubmitAnswer` по его часам). Все записи повторяемы: id создаёт
  клиент, ответ — ключ `step_pid`, запись таблицы — целиком.
- **Схема PostgreSQL:** `users` (`id`, `email` — уникальна без регистра, `name`, `role`, `active`,
  `password_hash`, `must_change_password`; миграция `0001_accounts.sql`), `auth_sessions`
  (`token_hash`, `user_id`, `expires_at`), `devices`, `games` (`content jsonb`), `media`,
  `sessions` (`state jsonb`, `phase` — вычисляемая из `state->>'phase'`, `leaderboard jsonb`,
  `version`, `updated_at` при каждом действии пульта; уникальный `code` среди `lobby`/`playing`),
  `participants`, `answers` (ключ `session_id, step, pid`), `results`. id из Firebase сохраняются.
  Формат содержимого и шага знает механика: `content`, `state`, `result` и `leaderboard` — jsonb
  без жёсткой схемы в базе, чтобы без миграций появились раунды, табло раунда и общий счёт,
  пьедестал, бонусные вопросы и ставки, суперигра с уровнями. Не закладываем в схему «один
  вопрос = один шаг», фиксированный набор полей шага или очков.
- **Клиент (`src/data/server/stream.ts`):** EventSource на подписку; обрыв — браузер переподключается
  сам и получает новый снимок (гость сам возвращается в игру); снимок не пришёл за 8 с или поток
  закрылся — проверка опросом (настоящая ошибка → `onError`), после двух сбоев — опрос раз в 2 с
  (`GET /api/sessions/:id`, списки участников и ответов).
- **PR 4.1 (`server/src/live.ts`, миграция `0003_live.sql`):** устройства гостей — `POST /api/auth/device`
  (вошедший ведущий остаётся собой); `POST /api/sessions` (id от браузера, код уникален среди
  незавершённых — индекс `sessions_active_code`), `GET /api/sessions/by-code/:code[?host=]`,
  `GET /api/sessions?host=`, `GET /api/sessions/:id`, `POST /api/sessions/:id/apply|phase|leaderboard|finish`
  (одно изменение под блокировкой строки, `version + 1`, `updated_at`), участники
  `/api/sessions/:id/participants/:pid/join|rename|captain|touch`, `DELETE`, команды `/teams`, ответы
  `POST /api/sessions/:id/answers` (`canSubmitAnswer` по часам сервера, отвечает капитан участника,
  повтор — `rejected`), `GET|DELETE /api/sessions/:id/answers/:step[/:pid]`, итоги `/api/results/:id`
  (без входа) и `?host=`, часы `GET /api/time`. Итоги пишет сервер по своей таблице лидеров.
  Картинки по id открывает любой вошедший (`canViewMedia`) — экран зала и гости.
- **Честная живая игра (аудит 7 октября 2026):** `apply` принимает `expect { phase, step, stage }` —
  игра ушла вперёд (второй пульт, двойное касание) → 409 `failed-precondition`, пульт молча ждёт
  свежее состояние; кнопка пульта держится, пока своё изменение не придёт обратно (до 3 с). После
  «Завершить» `apply` меняет только `cue`, `music`, `mix`, `slide`. `addScore { pid: ±n }` (|n| ≤ 100 000)
  и `rename { pid: имя }` правят таблицу на сервере (быстрые «+10» складываются), `/leaderboard`
  только добавляет новых. «Показать ответ» считает очки по свежему списку ответов с сервера
  (`SessionControl.freshAnswers`, `answersRepo.list`). Телефон запоминает ответ по шагу и времени показа
  вопроса (после «Назад» можно ответить заново) и на своём сервере один раз сверяет часы. «Назад» с
  заставки раунда возвращает общий счёт и старт прошлого раунда (`result.prevRoundBase`). Поток событий:
  событие сериализуется один раз (`sseFrame`), отставший больше чем на 512 КБ телефон отключается и
  переподключается; клиент в режиме опроса раз в ~40 с снова пробует поток, при пропуске версии берёт
  снимок. Поиск по коду: 20 промахов за 10 минут на устройство и 200 на адрес (429); команда — одна на
  телефон капитана, не больше 100 в сессии (повтор после обрыва — та же команда). Автосохранение на своём
  сервере шлёт пачки по одной (без `keepalive`: его лимит 64 КБ на все запросы страницы).
- **PR 4.2 — уборка:** при входе admin в `/admin` — `POST /api/sessions/cleanup` (`canCleanupSessions`):
  сессии старше 30 дней (сервер не берёт срок свежее `retentionCutoff`, что бы ни прислал браузер)
  удаляются с участниками и ответами, до 100 за вход (`more`); незавершённая игра с таблицей лидеров
  сначала сохраняется в `results` (уже сохранённые итоги не перезаписываются). Раз в сутки (первый
  раз — через 10 минут после запуска) приложение само (`server/src/cleanup.ts`): удаляет файлы
  картинок без ссылок в `media` старше 7 дней, недописанные `*.tmp` старше суток и устройства
  гостей старше 180 дней (их cookie уже истекла). У основной и тестовой версии — своя база и папка. Офлайн-очередь: правки игр и картинки —
  в IndexedDB (переживают перезагрузку, `useAutosave` не меняется), записи пульта и ответы — в
  памяти с повтором. Часы — `GET /api/time` (три замера, лучший по задержке).
- **Медиа — картинки** вопросов и слайдов и **музыка ведущих** (раздел 7, «Музыка»). Видео на сервер
  не загружается никогда (только на устройстве экрана зала).
  - Файлы на диске вне базы: `/srv/joyrest/media/prod` и `/media/test` (в контейнере

  - **PR 3.2 (`server/src/games.ts`, `src/data/server/games.ts`, `media.ts`):** `GET /api/games?scope=agency`,

## 3. Роли и экраны

Роли пользователей:
- **admin** — владелец агентства: добавляет и отключает ведущих, ведёт общую библиотеку.
- **host** — ведущий: свои игры, копирование шаблонов, запуск сессий.
- **guest** — гость: анонимный вход по коду сессии, без регистрации.

Регистрация ведущих закрыта: аккаунт создаёт только admin в `/admin` (почта + имя).
Аккаунт создаётся через вторичный экземпляр Firebase Auth (`loadSecondaryAuth`), чтобы
админ не разлогинился; временный пароль показывается один раз и нигде не хранится,
ведущий меняет его в студии. Отключение (`active = false`) блокирует вход в студию и пульт,
создание сессий и игр (так же в правилах). Удалить аккаунт Auth без Cloud Functions нельзя,
поэтому ведущих не удаляем, а отключаем.

Квалификация, стаж и баллы ведущих (только свой сервер; миграция `0005_host_levels.sql`,
`server/src/staff.ts`, правило — `src/core/points.ts`, названия — `src/core/levels.ts`):
- Квалификацию ставит владелец вручную в `/admin` («⋯ → Квалификация и стаж»):
  `intern` Стажёр, `novice` Новичок (до 1 года опыта), `host` Ведущий (после года),
  `top` Топ-ведущий (больше 3 лет). Стаж — от даты «опыт с» (`users.experience_since`, по
  умолчанию — дата добавления; можно раньше, если вёл до JoyRest).
- Ведущий в студии видит только свою квалификацию и стаж. Баллы видит только владелец
  (`/admin`: сумма у каждого ведущего, «⋯ → Баллы» — история и ручное начисление).
- Баллы за игру начисляет сервер при «Завершить игру» (одна запись на сессию, таблица
  `host_points`): игра шла от «Начать игру» (`sessions.started_at`) не меньше 40 минут и
  подключилось больше 10 телефонов (участники-игроки по данным сервера, не по счётчику
  браузера), каждый из которых сам или его команда ответил хотя бы на 3 вопроса (`MIN_ANSWERED_STEPS`). До 20 телефонов — 1 балл, за каждые полные следующие 5 — +0,5 (23 → 1, 25 → 1,5).
  Репетиция баллов не даёт (она без сервера), автоочистка незавершённых игр — тоже.
- Вручную владелец добавляет или снимает баллы (шаг 0,5, от −100 до 100) с обязательным
  комментарием. API: `POST /api/users/:id/level` (`{ level, experienceSince }`),
  `GET|POST /api/users/:id/points`; уровень и «опыт с» — в профиле (`/api/auth/me`), сумма
  баллов — в `GET /api/users` (admin). Право — `permissions.canManageHosts`.

«Команда JoyRest» (только свой сервер; миграция `0007_profiles.sql`, `server/src/team.ts`): у
ведущего карточка — аватарка (1:1, до 512 px), обложка (3:1, до 1500 px; обе обрезаются по центру и
сжимаются на устройстве — `cropImage`) и «о себе» (до 300 символов). `/studio/profile` — «Мой
профиль», `/studio/team` — карточки всех активных ведущих (пункты меню студии). Видят все активные
ведущие и владелец (`permissions.canViewTeam`); в карточке нет почты, квалификации и баллов. Файлы —
`MEDIA_DIR/profile/<sha256>`, адрес картинки с отпечатком (`?v=`), кэш на год; заменённые убирает
ночная уборка. API: `GET /api/team`, `POST /api/team/me` (`{ bio }`), `PUT|DELETE /api/team/me/avatar|cover`,
`GET /api/team/:id/avatar|cover`.

Библиотеки игр: общую (`scope: "agency"`) правит только admin, ведущие запускают её игры
как есть или копируют в «Мои игры» (`scope: "personal"`, видит только владелец).

Предложения в библиотеку (только свой сервер; `server/src/proposals.ts`, миграция
`0004_proposals.sql`, таблица `library_proposals`): ведущий у своей личной игры —
«⋯ → Предложить в библиотеку» (`permissions.canProposeGame`; повтор, пока предложение ждёт, — то
же предложение). Статус на карточке игры: «На проверке», «В библиотеке», «Отклонена: причина».
Владелец (`canReviewProposals` — admin) на вкладке «Библиотека JoyRest» видит блок «Предложения
ведущих»: Посмотреть (игра ведущего только для чтения), Принять, Отклонить (причина до 300
символов). Принять — копия игры в общую библиотеку (владелец — admin, картинки — те же файлы);
игра, уже принятая раньше, обновляет ту же игру библиотеки (если её не удалили), а не плодит
дубль. Игра ведущего остаётся у него. API: `POST /api/proposals` (`{ id, gameId }`, id от
браузера), `GET /api/proposals?mine=1` (свои), `GET /api/proposals?status=pending` (admin),
`POST /api/proposals/:id/accept|reject`. В `firestore.rules` этого нет: Firebase-версия кнопок
не показывает (`proposalsRepo` — null).

База площадок (только свой сервер; миграция `0008_venues.sql`, `server/src/venues.ts`, общая логика —
`src/core/venues.ts`, экраны — `src/screens/venues/`):
- Ведущий после мероприятия показывает QR-код из студии («QR-анкеты», `/studio/qr`): «Для заведения» →
  `/v?from=<uid>` (анкета площадки, 9 блоков: заведение, контакты, гости и залы, мебель и рассадка,
  особенности, кухня и меню, оборудование, условия, фото) и «Для клиента» → `/r?from=<uid>` (запрос:
  событие, дата, гости, бюджет, пожелания «хотелось бы / обязательно» по критериям `CRITERIA`).
  Без входа, черновик — на телефоне; id создаёт браузер (повтор — та же анкета, тот же номер заявки).
- Анкеты без входа принимаются только при `VENUE_FORMS=on` (`sudo joyrest venues on|off`, settings.env;
  compose по умолчанию `off`, app-test — всегда `on`, а без переменной открыты только при адресах сайта
  `test.*` — `venueFormsOpen`; проверяет `venues.test.ts`). Кабинет и ссылки
  предложений работают всегда. Защита: ловушка `website`, 5 анкет и 5 заявок в час на IP, 60 в час всего.
- Файлы анкеты (до 5 фото и до 5 файлов меню; фото сжимает телефон до ~350 КБ, PDF меню — как есть,
  до 1,9 МБ) — `MEDIA_DIR/venues/<sha256>`, без входа только по одноразовому токену анкеты (2 часа,
  не больше заявленного числа), место для загрузки — общее `takeUploadSlot`. Ночная уборка удаляет
  файлы без ссылок в `venues.files` и в предложениях (`cleanupVenueFiles`).
- Кабинет `/venues` (владелец и ведущие с `users.venue_access` — `permissions.canManageVenues`; доступ
  выдаёт admin в `/admin` «⋯ → Открыть базу площадок»): вкладка «Анкеты заведений» — анкеты с QR на проверке
  (`source = form`, статус «Новая»): «Принять в базу» («Проверено») или «Не подходит»; вкладки «Площадки» (таблица с закреплённым
  названием, группы колонок, поиск, фильтр и сортировка по статусу и дате, дубли по телефону или
  адресу — `findDuplicates`), «Заявки клиентов» (номер, имя, телефон, запрос; фильтр и сортировка),
  поиск везде — `src/core/search.ts` (без регистра, ё = е, слова в любом порядке, телефон по цифрам) и
  `SearchField` с подсказками (не больше пяти, под полем),
  «QR-коды». Статусы с цветами (пастель, тёмный текст): площадка — Новая / Проверено / Работали / Не
  подходит, заявка — Новая / Предложение отправлено / Договорились / Отказ.
- Заявка `/venues/r/:id`: подбор `rankVenues` — вместимость и «обязательно» отсекают, остальное —
  процент (да 1, частично 0,5, не указано 0,25, нет 0), «Не подходит» скрыты. Галочками до 10 площадок →
  «Предложение клиенту»: сервер сам собирает снимок `venue_offers` без адреса, телефонов, людей и заметок
  (`offerItem`), ссылка `/o/<22 случайных символа>` открывается без входа, фото — только из снимка;
  «Скачать PDF» — печать страницы. Заявка из «Новой» становится «Предложение отправлено».
- **Архив и защита от случайных нажатий** (миграция `0010_archive.sql`): «Убрать в архив» у площадки,
  анкеты и заявки ставит `archived_at` (ничего не стирается), вкладка «Архив» — открыть и «Вернуть из
  архива» (`POST /api/venues/:id/restore`, `/api/venue-requests/:id/restore`). Площадки из архива не
  попадают в подбор и новые предложения. Любое изменение в кабинете (статус, заметки, правка анкеты,
  принять/отклонить, файл, предложение, архив) — только после окна «Вы точно уверены?» (`useConfirm`).

  несохранёнными изменениями — тоже через подтверждение.
- **Баллы за площадку:** анкету по QR ведущего приняли в базу («Проверено» или «Работали») — ведущему
  `VENUE_POINTS` = 10 баллов, один раз на площадку (`host_points.id = venue-<id>`, `venueEarnsPoints`,
  `src/core/points.ts`); за свою же анкету, принятую им самим, баллов нет. QR у каждого ведущего свой

- Telegram — бот заявок сайта (`LEAD_TELEGRAM_*`): «📝 Заявка №12: свадьба, 80 гостей, 19 июня 2027»,

- API: `GET /api/venue-forms/status`, `POST /api/venue-forms/venue|request`,
  `PUT /api/venue-forms/venue/:id/files/photo|menu` (`X-Upload-Token`), `GET /api/offers/:id[/photos/:sha]`;

Экраны (маршруты):

## 4. Режимы проведения

Ведущий выбирает режим при запуске сессии (в интерфейсе два варианта; `remote` в данных
остался для старых сессий и работает как `laptop`):
1. **С экраном зала** (`laptop`). Ноутбук, планшет или телевизор показывают вопросы, телефон —
   пульт (ведущий свободно ходит по залу).
2. **Без экрана.** Только телефон ведущего. Вопросы и варианты показываются прямо на
   телефонах гостей, ведущий читает вслух.

Режим участников:
- **solo** — каждый гость играет сам.
- **teams** — команды; к команде можно подключить несколько телефонов, ответ
  отправляет капитан, остальные видят вопрос.

Вся игровая логика работает с абстракцией «участник» (игрок или команда) и не зависит
от режима.

Смайлик к имени: при входе гость выбирает смайлик себе, а создатель команды — команде
(`EmojiPicker`, набор `src/core/emoji.ts` — 24 одиночных символа без модификаторов, по
умолчанию случайный, можно «Без смайлика»). Смайлик хранится в начале имени («🦊 Аня»), поэтому
виден везде, где имя, без изменения базы и правил; вместе со смайликом имя не длиннее
`NAME_MAX_LENGTH`. При повторном входе смайлик восстанавливается из запомненного имени.
В режиме команд смайлик выбирают только команде, имя игрока — без него. Под сеткой — строка
«Так вас увидят: 🦊 Аня». В надписях с градиентом (победитель на экране зала) имя выводит
`NameText`: смайлик отдельным элементом со своим цветом, иначе он прозрачен.

Скрытые названия и представление команд (`src/core/teams.ts`, `state.teams = { hidden, shown, sizes }`):
в лобби пульт «Скрыть названия команд» — экран зала показывает «Команда 1 ★★★» (звёздочки — телефоны
команды, `sizes` пишет пульт), «Представить команды» — по одной крупно в порядке подключения (`shown`),
в конце все вместе; «Начать игру» открывает названия в любом случае. Таблица поверх игры по кнопке
пульта — `state.peek = "total" | "round"` (общий счёт или счёт текущего раунда), плашка «Убрать»;
любое изменение `step`, `stage` или `phase` без `peek` убирает её само (сервер и репетиция).
«Наградить сейчас» (`awardNow`, `src/core/podium.ts`) — пьедестал по текущему счёту, когда на экране
нет открытого вопроса (`ready`, `reveal`, `board`); «Назад» с заставки возвращает на тот этап
(`result.podiumFrom`).

Все телефоны гостей раз в 30 с сообщают «я на связи» (`touch`); молчит дольше 75 с — не на связи
(`src/core/presence.ts`, точка в «Гостях» на пульте). На входе гость видит «Вы уже играли?» —
отключившихся игроков (`GET /api/sessions/:id/offline`) и входит за себя прежнего
(`POST …/participants/:pid/claim`): телефону выдаётся устройство того игрока, прежний телефон теряет
доступ; только за того, кто не на связи, если у телефона нет своего игрока в этой игре и ни этот
телефон, ни устройство того игрока не играют в другой идущей игре (устройство общее для всех игр);
проверка и перенос — в одной транзакции, лимит 5 попыток с телефона и 60 на игру за 10 минут. «Гости» на
пульте: «+ Добавить игрока/команду» (без телефона, только в таблице, id `m…`; ответов от них не ждём),
«Очки: добавить или снять» любым числом, переименовать, убрать.

Итоги: `results.started_at` и `finished_at` (миграция `0009_results_time.sql`) — «начало в 19:05 · шла
1 ч 12 мин» на странице итогов и в «Истории игр».

Просьба выключить VPN (`VPN_HINT`, `src/core/texts.ts`) — у QR на экране зала, на пульте и на
входе гостя.

## 5. Модель данных (Firestore)

```
users/{uid}                 role, name, active, email, createdAt
games/{gameId}              scope: "agency" | "personal", ownerId, title,
                            mechanic, themeId, ageRating: "0+" | "12+" | "18+",
                            playMode: "solo" | "teams" (по умолчанию при запуске),
                            content, createdAt, updatedAt (serverTimestamp)
games/{gameId}/media/{mediaId}         bytes (WebP/JPEG), mime, width, height,
games/{gameId}/media/{mediaId}-small   variant: "full" | "small", createdAt
sessions/{sessionId}        code, hostId, gameId, gameTitle, mechanic, gameSnapshot, themeId,
                            playMode: "solo" | "teams",
                            screenMode: "laptop" | "remote" | "none",
                            state { phase: "lobby" | "playing" | "finished",
                                    step, startedAt, revealed,
                                    stage: "ready" | "question" | "reveal" | "board" | "podium",
                                    timeLimit, answered, result },
                            leaderboard { [pid]: { name, kind, score, colorIndex?,
                                                   last?, captainUid?, roundBase?, move? } },
                            createdAt (serverTimestamp)
sessions/{id}/participants/{pid}   name, kind: "player" | "team", teamId, captainUid,
                                   joinedAt (serverTimestamp), seenAt? (сигнал капитана)
sessions/{id}/answers/{step_pid}   step, pid, uid, value, submittedAt (serverTimestamp)
clock/{uid}                 t (serverTimestamp) — смещение часов экрана зала и пульта
results/{sessionId}         hostId, code, gameTitle, mechanic, themeId, playMode,
                            playedAt, participantsCount,
                            board [{ name, score, colorIndex? }] (по убыванию очков),
                            savedAt (serverTimestamp)
```

Уточнения к модели (этап 1):
- `code` — 6 цифр, уникален среди незавершённых сессий. Сессия ищется запросом
  `where code == X` и `where state.phase in ["lobby", "playing"]` с лимитом 5: правила
  пропускают поиск по коду только для незавершённых сессий. После «Завершить игру» сессию по
  коду не найти; ведущий находит свою по `code` + `hostId`, admin видит все. Телефон гостя и
  экран зала запоминают id сессии (localStorage) и после завершения открывают её по id
  (`get` разрешён всем вошедшим), поэтому гость видит финал своей игры.
- Телефон гостя — документ участника с `pid = uid`, поэтому повторный вход не создаёт
  дубль. В режиме teams команда — отдельный документ `kind: "team"` с автоматическим id,
  её создатель — капитан (`captainUid`); телефоны участников команды ссылаются на неё
  через `teamId`. В `leaderboard` попадают только игроки (solo) или только команды (teams).
- Экран зала не слушает участников: пульт ведущего переносит новых участников в
  `leaderboard` с нулём очков, и экран видит их через документ сессии.
- `colorIndex` есть только у команд: пульт выдаёт следующий по порядку цвет команды
  при добавлении в `leaderboard`, и цвет больше не меняется.
- Владелец агентства определяется по UID, зашитому в `firestore.rules` и
  `src/data/config.ts`; его профиль `users/{uid}` создаётся при первом входе. Его нельзя
  отключить, понизить или удалить.

Уточнения к модели (этап 2):
- История игр — коллекция `results`: компактные итоги без ответов и участников. Пульт пишет
  их одной пачкой вместе с `state.phase = "finished"` при завершении игры. `participantsCount` —
  число телефонов гостей. Итоги открываются по ссылке без входа (`allow get: if true`: там
  только названия и очки), списком — только своему ведущему и admin.
- Автоочистка без Cloud Functions: при каждом входе admin в `/admin` удаляются сессии старше
  30 дней (`src/core/retention.ts`) вместе с участниками и ответами — до 100 сессий за вход.
  Если у сессии с участниками ещё нет итогов (игру не завершили), admin сначала сохраняет их.
- Запросы без составных индексов: списки игр, сессий и итогов фильтруются только по
  равенству (или одному диапазону `createdAt`) и сортируются в браузере.

Уточнения к модели (этап 3, конструктор):
- Картинки не хранятся в документе игры и не копируются в `gameSnapshot`: в вопросе только
  `imageId`. Картинка сжимается на устройстве ведущего (`src/components/media/compressImage.ts`):
  полная — WebP до 1280 px по длинной стороне и ~150 КБ (Safari на iPhone не кодирует WebP —
  тогда JPEG), уменьшенная — до 480 px, ~35 КБ. Оба варианта пишутся одной пачкой в
  `games/{id}/media` (`MediaRepository`); правила пропускают не больше 400 КБ на документ.
- Картинку по id читает любой вошедший (`get`): экран зала и телефоны гостей входят анонимно.
  Списком — только тот, кто правит игру. Перезаписать нельзя, только создать или удалить.
- Экран зала загружает картинки сам и заранее (текущий и следующий вопрос). Телефоны гостей
  картинки не грузят, кроме режима «без экрана» — там уменьшенная версия.
- Копия и дубль игры (`gamesRepo.copy`) копируют картинки с теми же id: первая пачка создаёт
  игру вместе с картинками (правила проверяют права через `getAfter`). Удаление игры удаляет
  все её картинки, саму игру — последней пачкой. Картинку, загруженную и тут же заменённую
  или убранную в конструкторе, удаляем сразу; старые остаются до удаления игры, потому что
  на них может ссылаться уже запущенная сессия.

Уточнения к модели (этап 4, квиз в игре):
- Шаг игры проходит этапы `state.stage`: `ready` («Вопрос 2 из 8», ведущий ещё не показал) →
  `question` (таймер: `startedAt` ставит сервер, `timeLimit` — секунды) → `reveal` (правильный
  ответ, `revealed = true`) → `board` (таблица) → следующий шаг. «Назад» возвращает на этап:
  с `reveal` очки шага снимаются (`last`), с `question` ответы шага удаляются.
- Ответ принимается, только пока `stage == "question"` и не вышло время (`request.time ≤
  startedAt + timeLimit + 3 с` в правилах — запас на сеть). То же в `permissions.canSubmitAnswer`.
- `state.answered` — счётчик ответов для экрана, пульт пишет его не чаще раза в 2 секунды.
  `state.result` — итоги шага от механики (квиз: распределение по вариантам, сколько верно,
  засчитанные ведущим открытые ответы `accepted`).
- `leaderboard[pid].last` — очки за последний показанный ответ («+100» на экране и телефоне).
  Места при равных очках общие (10, 10, 7 → 1, 1, 3) — `rankedLeaderboard`.
- Одинаковые имена: пульт вносит в таблицу «Аня», «Аня 2» (`uniqueName`), документ участника
  не трогает. Ручные правки пульта: ± очки, переименовать, убрать участника.
- Команды: капитан известен телефонам из `leaderboard[teamId].captainUid`. Телефон капитана раз
  в 30 с пишет `seenAt`; если сигнала нет 90 с (или телефона капитана нет), пульт делает
  капитаном следующего по времени входа участника команды (`captainChanges`), ведущий может
  назначить капитана сам.
- Телефон запоминает свой ответ (localStorage); после перезагрузки посреди шага и участник
  команды при показе ответа читают ответ по id (`answersRepo.getOwn`): правила пускают `get`
  своего ответа и ответа своей команды, списком ответы видит только пульт.
- Часы: экран зала и пульт один раз пишут `clock/{uid}` с serverTimestamp и читают его, чтобы
  таймер совпадал с сервером. Телефоны идут по своим часам (экономия операций).
- «Репетиция» (`/studio/rehearsal/:id`) — тот же пульт и экран зала на сессии в памяти
  (`core/session.applyChange`), без гостей и без записей в базу.
- Демо-квиз (8 вопросов, `src/mechanics/quiz/demo.ts`) admin добавляет в «Библиотеку JoyRest»
  кнопкой на вкладке библиотеки (`demoGames` в реестре).

Правила экономии лимитов:
- Гости и экран зала слушают **только документ сессии**. Таблица лидеров хранится в нём.
- Ответы слушает только пульт ведущего.
- При запуске сессии игра копируется в `gameSnapshot`: правка игры в конструкторе не
  ломает идущую сессию.
- Ответ гостя пишется одним документом с детерминированным id `step_pid`, поэтому
  повторное нажатие не создаёт дубль.

Подсчёт очков выполняет пульт ведущего (Cloud Functions на бесплатном тарифе нет).
Правила безопасности разрешают менять `state` и `leaderboard` только владельцу сессии.
Удалять сессии может владелец и admin (автоочистка).

Честность вопросов на скорость: время ответа = `submittedAt − state.startedAt`, оба
значения ставит сервер (`serverTimestamp`). Часам телефонов не доверяем.

## 6. Механики как модули

Каждая механика — отдельная папка `src/mechanics/<id>/` с единым интерфейсом:

```ts
interface Mechanic<Content, Answer> {
  id: string;
  title: string;
  supports: { solo: boolean; teams: boolean; noScreen: boolean };
  Editor: Component;        // конструктор
  ScreenView: Component;    // экран зала
  PlayerView: Component;    // телефон гостя
  HostControls: Component;  // пульт
  create(): Content;            // содержимое новой игры
  parse(raw): Content;          // данные из базы → формат механики, без исключений
  mediaIds(content): string[];  // картинки игры (копируются вместе с ней)
  steps(content): Step[];   // последовательность шагов игры
  score(step, answers, { state }): ScoreDelta[]; // state: startedAt, timeLimit, result
  validate(content): ValidationError[]; // path "questions/<id>/<поле>" + понятная подсказка
}
```

`HostControls` получает ответы на шаг, участников и `SessionControl` (`apply` — одна запись
состояния и таблицы, `clearAnswers`, `requestFinish`): на настоящей сессии он пишет в базу, в
репетиции — в память. `PlayerView` получает `pid` (кто получает очки), роль телефона
(`player`/`captain`/`member`) и свой ответ. Ход квиза — чистые функции `quiz/flow.ts`.
Очки за скорость: самый быстрый верный ответ — максимум, ответ в последнюю секунду — половина.

Ядро и экраны работают с механикой из реестра как с `AnyMechanic` (содержимое `unknown`)
и всегда сначала вызывают `parse`. Игру с ошибками `validate()` запустить нельзя: кнопка
«Запустить» неактивна, экран запуска показывает, что исправить. Конструктор механики —
отдельный чанк (`lazy`), телефону гостя он не нужен.

Пьедестал (`src/core/podium.ts`, `src/components/live/Podium.tsx`) — общий для всех механик
этап `state.stage = "podium"` после таблицы последнего шага. Пульт: «Награждение» (заставка) →
«Показать 3 место» → «Показать 2 место» → «Показать 1 место» → «Завершить игру»; «Назад» закрывает
места по одному, с заставки — к таблице. Сколько мест открыто — `state.result.podium` (остальное
в `result` не трогается). На пьедестал попадают места 1–3 с очками больше нуля, при равных очках —
на одной ступени (до трёх имён, «и ещё N»), пустое место пропускается; если очков ни у кого нет —
сразу «Завершить игру». Экран зала: ступени 2 · 1 · 3, имя со смайликом, цвет команды, очки; на
первом месте — фанфары и салют (только CSS, при «уменьшить движение» салюта и анимаций нет). Телефон
гостя: «Награждение! Смотрите на экран», своё место — когда до него дошли; открытые места списком
(для режима без экрана). Финал экрана зала — тот же пьедестал целиком и таблица. Экран зала и
телефон показывают пьедестал сами, механика его не рисует; механика только ведёт пульт к нему.

Раунды и табло (`src/core/rounds.ts` — общая арифметика, где раунды — решает механика). В записи
таблицы `roundBase` — очки на старте раунда (очки раунда = `score − roundBase`), `move` — на сколько
мест сдвинулся после последнего ответа («↑2», «↓1»). Квиз: у вопроса `round` — название раунда,
который с него начинается (null — продолжает прежний; ни одного названия — раундов нет; вопросы до
первого названия — «Раунд 1»). Импорт списком: строка «# Раунд: Кино» перед вопросом. Пульт: в
начале раунда — «Начать раунд» (экран — заставка раунда), после последнего вопроса раунда —
«Итоги раунда» (`result.board = "round"`: таблица раунда, ★ у лучших в раунде) → «Общий счёт»
(`"total"`: таблица со стрелками и ★) → следующий раунд (`roundBase = score` у всех). Телефон: место
и очки в раунде, «★ Лучший в раунде!», стрелка у своего места. Таблица в середине раунда — со стрелками.

Квиз (`src/mechanics/quiz/`): вопросы `choice` (2–6 вариантов, верных — один или несколько: `correct` +
`alsoCorrect`, засчитывается любой; в импорте несколько «*»), `open` (несколько
верных ответов, сравнение без регистра, ё/е, пробелов и пунктуации — `normalize.ts`),
`speed` (варианты, очки по времени); у каждого время, очки и картинка. Настройки проведения
(`content.settings`, `settingsOf`; в конструкторе «Как проводить»): `intro` — заставка «Вопрос 2 из 8» (без
неё «Следующий вопрос» сразу открывает вопрос, заставка раунда остаётся), `board` — таблица `each` после
каждого вопроса, `rounds` только в конце раунда (без раундов — в конце игры), `manual` по кнопке «Показать
таблицу» (`extraAction`), `phoneImages` — картинка вопроса на телефонах и при экране зала. Импорт списком
(`importText.ts`): вопрос с новой строки, варианты с «-», верный с «*», открытый ответ
«= ответ1 | ответ2», раунд — «# Раунд: Кино». Виды экрана зала размечены в единицах контейнера (`cqw/cqh`), поэтому
предпросмотр в студии совпадает с телевизором.

«Своя игра» (`src/mechanics/board/`, механика `board`): поле — строки-категории × колонки-стоимости
(до 8×8), в клетке вопрос, трек (фрагмент, припев, конфетти), картинка или «Кот в мешке». Ход
(`board/logic.ts`, `state.result`: `opened`, `cell`, `picker`, `mode`, `buzz`, `bets`, `fines`, `prev`):
`ready` — поле, ведущий касается клетки → `question` с кнопкой «кто первый» (`core/buzz.ts`) →
«Верно» (стоимость клетки, право выбора) / «Неверно» (слово следующему; с галочкой «штраф» — минус
стоимость) → `reveal` → «К полю»: следующий шаг, клетка гаснет до конца поля. «Кот в мешке»: шаг
ставок (`{ bet }`, до своего счёта или стоимости клетки, `betTime` секунд), потом шаг вопроса — отвечают
только поставившие, верно — +ставка, остальные поставившие — −ставка. «Назад» с каждого этапа
(штрафы возвращаются). Все клетки сыграны — пьедестал. Пульт сам показывает крупную «Таблица очков на
экран» (`ownPeek`, `state.peek`). Шаблон — `board/demo.ts`.

Очередь новых форматов (решения владельца 8 октября 2026): «Шашки» (противоборство двух команд:
ход получает команда, верно и быстрее ответившая на вопрос; 10 очков за шашку, 30 за дамку, 50 за
победу; вопросы кончились — побеждает больший счёт), «Танцевальный батл» (карточки Батл/Танец/
Караоке, оценки других команд 10–100, голос зала; видео — файл на устройстве экрана зала или ссылка,
на сервер не загружается), «Активная настолка» (поле ~40 клеток, кубик бросает сервер, в клетке —
вопрос, танец, караоке, активное задание или бонус/ловушка; шаблоны «Классика» и «18+»).

Новая механика подключается регистрацией в `src/mechanics/registry.ts` и не требует
изменений в ядре. Ядро ничего не знает о конкретных играх.

Очередь механик:
1. Квиз: варианты ответа, открытый ответ, на скорость, вопрос с картинкой и аудио.
2. «Угадай мелодию» и музыкальное лото.
3. Тайные роли: Мафия, Бункер, Шпион.
4. Игровые поля: Just Dance Battle, ходилки «Алкогольные / Сладкие приключения».
5. Голосования: Битва тостов, Замри.

## 7. Музыка и медиа

- На сервер загружаются картинки (вопросы, слайды) и **музыка с чистыми правами** (ниже); видео — никогда.
- **Музыка** (решение владельца 7 октября 2026; миграция `0006_tracks.sql`, `server/src/tracks.ts`,
  студия — вкладка «Музыка», `src/screens/studio/MusicTab.tsx`): ведущий загружает трек себе (mp3,
  m4a, ogg до 15 МБ, тип — по первым байтам; 500 МБ на ведущего; при свободном месте < 3 ГБ —
  отказ), выбирает, для чего он (лобби, фон, конкурс, таблица, перерыв, награждение, праздник —
  `src/core/music.ts`), и обязательно отмечает, откуда права: Pixabay, куплен, свой или «другое» с
  пояснением. «Предложить в общую» → владелец на той же вкладке слушает и принимает (запись-копия
  со `scope = agency`, файл тот же; повторно принятый обновляет ту же копию) или отклоняет с
  причиной. Админ загружает сразу в общую. Права — `permissions.canUploadTrack|canUseTrack|
  canEditTrack|canShareTrack|canReviewTracks` (в `firestore.rules` нет: Firebase-версия музыки не
  показывает, `tracksRepo` — null). Файлы — `MEDIA_DIR/audio/<sha256>` (вне корня картинок: уборка
  картинок прошлых релизов их не трогает), лишние убирает ночная уборка (`cleanupAudio`), копируются
  ночным restic вместе с `media/prod`. API: `GET /api/tracks` (свои + общие), `?status=pending`
  (admin), `POST /api/tracks` (описание, id от браузера), `PUT /api/tracks/:id/file` (файл как есть,
  `X-Duration` — мс), `GET /api/tracks/:id/file` (любой вошедший — экран зала; кэш как у картинок),
  `PATCH|DELETE /api/tracks/:id`, `POST /api/tracks/:id/share|accept|reject`.
- Музыка на мероприятии: пульт (`MusicPanel`, если режим не «без экрана», и после завершения игры)
  пишет `state.music = { trackId, playing, rev }` (новый `rev` — трек с начала) и микшер
  `state.mix = { music, effects, muted }` (0–100, ползунок — не чаще раза в 0,3 с). Экран зала
  (`useHallMusic`) качает файл один раз, играет по кругу через Web Audio (шины музыки и эффектов в
  `sound.ts`), под эффекты музыка приглушается до 30% и возвращается. Браузер не дал включить звук —
  на экране «Коснитесь экрана, чтобы включить музыку». Пока браузер экрана не включил звук (не было
  касания), экран просит «Коснитесь экрана, чтобы включить звук» (`useSoundReady`), пульт после
  нажатия кнопки звука пишет «На экран зала: Гонг». На телефонах гостей звука нет.
- Раньше (и как запасной вариант): аудиофайлы выбираются с устройства ведущего и хранятся локально
  (IndexedDB) на том устройстве, где открыт экран зала. На сервер не загружаются.
- В игре хранится только ссылка на трек: имя файла, начало фрагмента, длительность.
- Если файла нет на устройстве, экран зала показывает понятное сообщение и предлагает
  выбрать файл заново.
- Запасной режим «свой плеер»: платформа показывает только кнопки и считает очки.
- Звук играет только на экране зала, никогда на телефонах гостей.
- **Звуки** (`src/components/live/sound.ts`) синтезируются в браузере экрана зала (Web Audio), без
  файлов и лицензий: тиканье, «время вышло», верный ответ, свист заставки раунда, фанфары и
  аплодисменты пьедестала, гонг, барабанная дробь, «ошибка». Кнопки на пульте (`SoundPad`, если
  режим не «без экрана»): Гонг, Барабанная дробь, Фанфары, Аплодисменты, Ошибка, Стоп. Пульт пишет
  `state.cue = { id, sound }` (`src/data/cues.ts`, сервер принимает только известные звуки), экран
  играет звук при новом id и не играет при открытии; «Стоп» глушит всё, что звучит.
  Звук разрешается любым касанием, кликом или клавишей, сколько угодно раз (`useSoundUnlock`: браузер
  даёт звук на отпускание пальца; iOS снова приостанавливает его после блокировки экрана), плашка
  «Коснитесь, чтобы включить звук» — кнопка; на iPhone/iPad `audioSession = playback` (иначе молчит в
  беззвучном режиме). Кнопка на экране называет действие («Включить звук» / «Выключить звук»);
  выключенный звук не запоминается. Экран раз в 20 с сообщает о себе (`POST /api/sessions/:id/screen`,
  только память сервера, `screenRepo` — null у Firebase), пульт показывает в строке статуса «экран на
  связи · звук ✓» или что сделать (`GET …/screen`, только ведущий, молчит минуту — «не открыт»).
- **Слайды-шаблоны** (`src/core/slides.ts`, `SlideView`, пульт — `SlidesPanel`, если режим не «без
  экрана»): заставка вечера, правила (до 8 пунктов), раунд, перерыв (обратный отсчёт по часам
  сервера, `endsAt`), награждение, спасибо (QR канала t.me/JoyRest), свой слайд. Пульт пишет
  `state.slide = { id, kind, title, text, lines, endsAt }` (`parseSlide` в `src/data/cues.ts`,
  сервер обрезает длинное и не принимает неизвестные виды), экран зала показывает слайд поверх
  любой фазы игры на живом фоне темы, со звуком при новом `id`; `slide: null` — обратно к игре.
  Тексты шаблонов ведущий правит на пульте, они запоминаются на устройстве (localStorage).
- Фоновая музыка — треки ведущих с чистыми правами (Pixabay Content License, купленные, свои),
  общие — после проверки владельцем (см. «Музыка» выше).

## 8. Темы оформления

Тема — это данные, а не код: палитра, шрифты, фон, звуки, анимации.

```
themes/<id>.ts   id, title, kind: "brand" | "seasonal" | "occasion",
                 tokens { colors, fonts, radius, background }, sounds, ageRating
```

- Базовая тема — фирменный стиль JoyRest.
- **Темы-концепции** (`src/themes/concepts.ts`): «Новый год» (снег, гирлянда, колокольчики), «Гэтсби»
  (ар-деко, золотые веера, блик, джаз), «Голливуд» (лучи прожекторов, вспышки камер), «Диско»
  (огни, зеркальный шар, диско-звуки), «Свадьба» (светлая, лепестки, нежные звуки). У темы
  `effects { scene, garland?, shine?, soundSet, particle, glow }`: живой фон `Scene`
  (`src/components/live/Scene.tsx` — экран зала, предпросмотр в студии, репетиция и выбор темы при
  запуске; телефоны и пульт — только цвета), блеск крупных надписей (`[data-shine="on"]`, градиент
  `code` с бликом посередине), набор синтезированных звуков (`setSoundSet` в `sound.ts`: тиканье,
  верный ответ, фанфары). Фон — только CSS transform/opacity, до ~40 частиц; при «уменьшить
  движение» частиц и бликов нет. Цвета фона — из темы (`--scene-particle`, `--scene-glow`).
  Украшения живут у краёв и под текстом, середину и верхнюю строку (счётчик, таймер) не закрывают:
  звёзды — по бокам, шар диско — на нитке в правом поле, веера и рамка — по углам.
- Сезонные: Новый год, 23 февраля / 8 марта, лето, Хэллоуин и т.д.
- Тематические: свадьба, корпоратив, детский праздник, 18+.
- Компоненты используют только CSS-переменные из токенов, никаких цветов «в коде».
- Возрастные ограничения: контент и темы 18+ не предлагаются в детских играх.

  и `text`). «Скопировать ссылку», «В студию», «Выйти».

- **плитка** `.tile` (только пульт и выбор роли устройства) — квадрат с контурной картинкой
  (`src/components/Icon.tsx`) и короткой подписью: звуки, шаблоны слайдов, «Пульт / Экран зала».
- Высота любой кнопки и поля ввода — не меньше 52px (сейчас 56px, `--control-height`).
  На телефоне кнопки блока стоят столбиком во всю ширину (`.actions`), без переносов в ряд.
- Компьютер (от 1024px): страницы с шапкой шире (960px, пульт — 720px), карточки игр в две колонки,
  кнопки карточки в ряд; в шапке не больше трёх кнопок, остальное — в «Ещё» (`TopBar`).

Выбор вариантов — карточки `.choice` со своей радиокнопкой (никаких системных кружков):
- невыбранная — тонкое кольцо 2px цвета `control` (#B5ABA2), карточка с обычной рамкой;
- выбранная — кольцо и точка цвета `controlChecked` (#C49E96), карточка с обводкой
  `highlight` (#E3C68C). В дневной теме — #7A6E66, #8A5148 и #9A7444 (иначе контраст < 3).
- Внутри: `.choice__title` (жирный) и `.choice__hint` (второстепенный).

Шапка — компонент `TopBar`: монограмма, «JoyRest Games» одной строкой, название экрана.
Действия передаются списком `actions`: на телефоне — одна кнопка-меню ☰, от 720px —
вторичные кнопки в ряд.

QR-код — только компонент `QrCode` (`src/brand/qrSvg.ts`): кремовая скруглённая плашка
#FBF6F1, модули #221E1B, тихая зона 4 модуля со всех сторон, уровень коррекции H,
монограмма J✦R в центре на кремовой подложке не больше 20% ширины кода. Цвета не зависят
от темы. Тест `src/brand/qrSvg.test.ts` растеризует код и распознаёт его (jsQR) —
после любых правок QR он должен быть зелёным.

Код игры — `.big-code`: без переносов, Cormorant 700, градиент темы; контраст обоих
концов градиента с фоном и с карточкой ≥ 4.5 проверяет тест контраста.

Сетка и поля:
- отступы кратны 8px (8, 16, 24, 32); внутренний отступ карточек 24px, промежутки 16px;
- поля страницы на телефоне 20px, учитываются `safe-area` сверху, снизу и по бокам;
- снизу у страницы запас 88px (`--bottom-clearance`): плавающая панель Netlify на тестовых
  ссылках и уведомления не перекрывают контент;
- заголовки с `text-wrap: balance`, длинные строки (адрес, код) — в одну строку с обрезкой.

Вкладки — компонент `Tabs`: тихие кнопки, у выбранной полоса градиента снизу, стрелки
переключают. Дополнительные действия карточки — кнопка «⋯» (`ActionMenu`, тот же список,
что меню ☰ в шапке). Необратимые действия («Удалить игру», «Отключить») — только через
`ConfirmDialog`. Подробности карточки (механика, тема, число вопросов, дата) — плашки `.meta`.

Загрузка: вместо текста «Загружаем…» — каркас экрана (`src/components/Skeleton.tsx`)
через `Pending`. Медленная сеть — не ошибка: загрузка не прерывается и сама повторяется после
сетевых сбоев с паузой 2, 4, 8, дальше каждые 10 секунд (`withRetry` в `src/data/retry.ts`).
Через 8 секунд под каркасом — плашка «Подключаемся… интернет медленный, подождите» с
индикатором и маленькой кнопкой «Обновить страницу», через 30 секунд — «Всё ещё подключаемся —
проверьте связь или Wi‑Fi». Данные пришли — экран открывается сам. Ошибкой с остановкой
(`LoadFailed`) показываются только настоящие ошибки: не найдено, нет доступа (`isPermanentError`).
Обрыв связи во время работы — тонкая полоса сверху «Нет связи — переподключаемся…»
(`ConnectionBanner`, источник — `connection` из слоя данных), после восстановления — короткое
«Связь восстановлена»; экран не закрывается, подписки Firestore догоняют данные сами.
Уведомления о действиях — `Toast` («Ссылка скопирована»).

Скорость: Firebase грузится динамически (`src/data/firebase.ts`) через обёртки
`src/data/sdk/*.ts` с именованным реэкспортом — новую функцию SDK добавляйте туда,
иначе пропадёт tree-shaking. Экраны — отдельные чанки (`lazy` в `App.tsx`); главная и
`/j` не грузят Firebase.

`src/components/Logo.tsx` (импорт `?inline-svg`, метаданные вырезаются при сборке). Цвет —

заголовком; монограмма
в левом нижнем углу экрана зала во время игры и после неё (сверху её закрывали счётчик и заголовки); полный логотип над формой входа гостя;

## 9. Надёжность — обязательные требования

- Гость, у которого погас экран или пропал интернет, возвращается в игру автоматически
  и видит текущий шаг.
- Если ведущий закрыл вкладку, игра продолжается с того же места после открытия пульта.
- Слабый интернет на площадке — норма: на телефон гостя передаём минимум данных,
  тяжёлые медиа только на экране зала.
- Нагрузочный симулятор `scripts/simulate.ts`: запускает N виртуальных гостей
  (до 500) против тестовой сессии. Прогонять перед каждым релизом механики:
  `GUESTS=500 npm run simulate` (`TEAMS=1` — режим команд). Демо-квиз, 8 вопросов:
  50 гостей — ~4,4 тыс. чтений и ~510 записей на игру; 500 гостей — ~34 тыс. чтений и
  ~4,5 тыс. записей (лимит Spark в сутки: 50 тыс. чтений, 20 тыс. записей). Основные
  статьи: гости слушают документ сессии (~45–60 обновлений за игру) и проверки правил
  при ответе (2 чтения на ответ).
- Нагрузка на своём сервере (этап 7): `scripts/load.ts` — N гостей (до 1000) через настоящие
  REST и потоки событий на test.games.joy-rest.ru (другой адрес — отказ), пульт и экран зала
  как в браузере. Итог: выдача устройства, вход, доставка вопроса на телефоны, приём ответа
  (медиана, 95%, максимум), потерянные ответы, переподключения. Не пройдено — ошибки,
  потерянный ответ или доставка вопроса 95% телефонов дольше 2 с. Запуск — workflow
  «Нагрузка» (`.github/workflows/load.yml`, Run workflow или коммит с `[load]` в ветке
  `claude/*`); ведущий — `load@joy-rest.ru` на test, пароль — секрет `LOAD_HOST_PASSWORD`.
  Память и процессор сервера во время прогона — `joyrest status` или статистика в панели Beget.
- Проверка глазами гостя: `scripts/e2e/guest.mjs` — настоящий браузер (Playwright, ставится
  только в workflow «Проверка гостем», `.github/workflows/e2e.yml`, в зависимостях его нет)
  проходит игру на test: вход гостей со смайликом и без, пульт, экран зала, ответ, таблица,
  финал, итоги, режим команд, страницы студии (музыка, профиль, команда). Проверяет имена со смайликом на телефоне, пульте и экране,
  просьбу про VPN, ошибки страницы, прокрутку вбок и кнопки меньше 44 px на телефоне. Итог —
  аннотацией в Actions; снимки в Telegram не шлём (владелец попросил). Запуск — Run workflow или коммит с
  `[e2e]` (ждёт, пока этот коммит выложится на test). Ведущий — тот же `load@joy-rest.ru`.
- Сценарий обычного вечера (`scripts/scenario.ts`, workflow «Сценарий 35 гостей», Run workflow или
  коммит с `[scenario]`): 35 гостей solo и 7 команд по 5 на test; каждый механизм по три раза в разном
  порядке — показ, «Назад» с вопроса и ответа, двойное касание, отставший пульт, раунды и «Назад» через
  начало раунда, ручные очки и переименование, звуки, музыка, микшер, слайды поверх вопроса, статус экрана,
  переподключение гостей, смена капитана, награждение вперёд-назад, завершение и что можно после него.
  После каждого шага: очки = модель по ответам с сервера, экран и телефоны видят ту же версию, ни одного
  5xx, гостю не уходят пароли, токены, почты и доступы к базе; гость не управляет игрой.
  Там же шаг «Студия и владелец» (`scripts/studio.ts`, нужны секреты `TEST_ADMIN_EMAIL` и
  `TEST_ADMIN_PASSWORD` — владелец на test): ведущий `studio-check@joy-rest.ru` (создаётся один раз, в
  конце отключается), временный пароль и свой, закрытие других сеансов, права ведущего, квалификация и
  баллы, профиль и «Команда», игры (12 правок подряд, большая игра, картинки, копии), предложения в
  библиотеку, музыка и проверка владельцем, история и автоочистка, отключение и включение ведущего;
  каждая запись перечитывается. Там же шаблоны библиотеки (демо-квиз, «Угадай мелодию», музыкальное
  лото): есть в библиотеке test (нет — добавляются, как кнопкой владельца), проходят `validate`,
  копируются; лото играется целиком (карточка гостя, песни, «Лото!», очки, итоги).
- Экран зала и телефон гостя не гаснут во время игры (Wake Lock, `useWakeLock`).
- Конструктор сохраняет изменения автоматически, ни одна правка не теряется
  (`src/components/useAutosave.ts`: пачка правок через 0,7 с уходит сразу, не дожидаясь
  ответа на предыдущую, — запись ложится в очередь локального кэша Firestore и переживает
  обрыв связи и закрытие вкладки; после отказа сервера — повтор со свежими значениями;
  досылка при сворачивании вкладки). Индикатор: «Сохранено», «Сохраняется…», «Нет связи»
  (браузер офлайн или сервер молчит дольше 5 с).

## 10. Правила разработки

- Маленькие задачи, понятные коммиты на русском языке.
- Каждая механика покрыта тестами логики `steps` и `score`.
- Правила безопасности Firestore лежат в `firestore.rules` и покрыты тестами.
  После изменения правил напиши владельцу пошагово, как вставить их в консоль Firebase.
- Секреты в репозиторий не кладём. Конфигурация веб-приложения Firebase не секретна;
  ключи сервисного аккаунта запрещены. Токены ботов и API — только на сервере
  (`/srv/joyrest/secrets.env`, раздел «Сайт агентства»).
- Интерфейс: сначала мобильная версия для гостя, крупные кнопки, видимый фокус,
  уважение к настройке «уменьшить движение».
- Тексты интерфейса простые и конкретные: кнопка называет действие («Начать игру»,
  «Показать ответ»).
- После каждой завершённой задачи кратко сообщай, что проверить по тестовой ссылке.
