## 1. Решение, которое фиксируем

JoyRest должен поддерживать **два способа физического ввода через один продуктовый интерфейс**:

1. **Сторонние Bluetooth-кнопки**, подключённые к компьютеру ведущего через локальную программу «JoyRest Кнопки».
2. **Беспроводные комплекты с одним USB-приёмником**, поддерживаемые через открытый HID-интерфейс, SDK или адаптер локальной программы.

Оба источника:

- назначаются командам или отдельным игрокам в одном разделе пульта;
- могут работать в одной сессии одновременно;
- проходят один режим проверки;
- попадают в существующую очередь «кто первый»;
- записываются как существующий ответ `{ buzz: true }`;
- получают окончательное время и порядок на сервере;
- не требуют отдельной версии игровых механик;
- имеют телефон как резервный канал.

**Не создаём две разные функции «Bluetooth-кнопки» и «USB-кнопки».** Создаём общую подсистему «Физические кнопки» и два аппаратных адаптера.

---

## 2. Цель продукта

Дать ведущему возможность проводить игры на скорость реакции без обязательного использования телефонов:

- команда получает физическую кнопку;
- ведущий один раз связывает её с командой;
- перед игрой быстро проверяет все кнопки;
- во время вопроса видит знакомую очередь нажатий;
- при отключении кнопки использует телефон или ручной резерв;
- при следующем мероприятии может выбрать Bluetooth или USB-комплект в зависимости от зала и оборудования.

### 2.1. Пользовательская ценность

- Меньше зависимости от мобильного интернета и состояния телефонов гостей.
- Более понятный и азартный физический ритуал нажатия.
- Возможность играть командам, добавленным ведущим «без телефона».
- Одинаковые правила и интерфейс для разных наборов оборудования.
- Быстрая диагностика до начала вопроса, а не после спорного нажатия.

## 3. Рабочие допущения MVP

Эти параметры не следует молча менять в процессе разработки:

| Параметр | Решение для MVP |
|---|---|
| Участники | Команды и отдельные игроки; далее в документе «участник» означает оба варианта |
| Количество | До 8 назначенных кнопок на сессию; архитектура не должна жёстко ограничивать расширение |
| Привязка | Одна активная физическая кнопка на участника; одна кнопка принадлежит только одному участнику |
| Источники | Bluetooth и USB; смешанная работа разрешена |
| Механики | Квиз «Гонка: кто первый», «Ставка на знания», «Сто к одному» |
| Управление | Пульт ведущего на компьютере, к которому подключено оборудование |
| Сервер | Только собственный Fastify/PostgreSQL-контур |
| Firebase | Физические кнопки не поддерживаются; интерфейс должен явно сообщать об этом |
| Телефон | Сохраняется как существующий и резервный способ нажатия |
| Подсветка | Используется только если оборудование её поддерживает; не является обязательной |
| Порядок | Только по серверному приёму; локальная временная метка не определяет победителя |
| Привязки | Сохраняются на сервере внутри конкретной сессии |
| Статусы связи | Хранятся локально, не записываются в PostgreSQL при каждом изменении |

### 3.1. Что не входит в MVP

- Прямое подключение кнопок к телефону гостя.
- Несколько физических кнопок, закреплённых за одной командой одновременно.
- Произвольные ответы, ставки, голосования и действия, кроме `{ buzz: true }`.
- Поддержка всех существующих механик JoyRest.
- Собственное производство оборудования.
- Гарантия совместимости с любой Bluetooth-кнопкой.
- Определение победителя по времени, которое сообщает кнопка или компьютер.
- Автоматический перенос привязок в другую игровую сессию без подтверждения ведущего.
- Обязательная работа USB-приёмников без локальной программы.

## 4. Что уже есть в JoyRest и что переиспользуем

### 4.1. Существующий игровой путь

В текущей архитектуре:

- телефон отправляет ответ через `AnswersRepository.submit`;
- серверный маршрут находится в `server/src/live.ts`;
- сервер проверяет текущий шаг, этап, время и права;
- ответ сохраняется в `answers`;
- сервер ставит `submitted_at`;
- событие публикуется в `Hub`;
- пульт получает ответы через SSE и синхронизирует очередь;
- `src/core/buzz.ts` сортирует нажатия и определяет текущего отвечающего;
- `src/components/live/BuzzButton.tsx` показывает состояние гостю.

### 4.2. Обязательное переиспользование

Не дублировать:

- таблицу ответов;
- правила приёма текущего шага;
- серверные часы;
- поток ответов;
- `buzzOrder`, `syncBuzz`, `buzzWrong`, `buzzRight`;
- пультовую очередь;
- начисление очков и показ отвечающего;
- механизм `expect` при закрытии вопроса;
- правила «Назад» и повторного показа вопроса.

### 4.3. Почему нужен отдельный серверный вход

Обычный `POST /api/sessions/:id/answers` проверяет, что за участника отвечает сам игрок или текущий капитан. Пульт ведущего не должен обходить эту проверку и не должен получать гостевой токен каждой команды.

Поэтому создаётся отдельный host-only маршрут для физического нажатия. Он использует те же правила записи, но имеет отдельную авторизацию ведущего и дополнительные проверки привязки.

### 4.4. Паспорта логики

Перед изменением конкретной механики:

- прочитать `src/mechanics/LOGIC.common.md`;
- прочитать `src/mechanics/quiz/LOGIC.md` для квиза;
- прочитать `src/mechanics/board/LOGIC.md` для «Ставки на знания»;
- перед подключением «Сто к одному» сначала проверить наличие и актуальность её `LOGIC.md`; если паспорта нет — восстановить и согласовать эталон логики отдельным шагом;
- любые изменения поведения внести в паспорт, инструкции и тесты в том же PR.

## 5. Термины и идентификаторы

| Термин | Значение |
|---|---|
| Устройство | Физическая кнопка или логическая кнопка внутри USB-комплекта |
| Источник | `bluetooth`, `usb`; для резерва дополнительно существует `phone` |
| `hardwareId` | Стабильный идентификатор устройства внутри адаптера; не является секретом |
| `bindingId` | Идентификатор серверной записи привязки устройства к участнику |
| `participantId` | Существующий `pid` игрока или команды JoyRest |
| Привязка | Связь `сессия + источник + hardwareId → participantId` |
| Помощник / программа | Локальное приложение «JoyRest Кнопки» на ПК ведущего |
| Проверка | Режим, в котором нажатия только отмечаются визуально и не создают ответов |
| Игровое нажатие | Событие, которое после серверных проверок становится `{ buzz: true }` |
| Локальное время | Время нажатия на ПК; используется только для диагностики |
| Серверное время | `submitted_at`; определяет порядок ответов |

**Нельзя привязывать кнопку к `uid` капитана.** Привязка выполняется к `participantId`, чтобы смена капитана и перезаход с телефона не влияли на неё.

## 6. Аппаратные требования

### 6.1. Обязательные свойства поддерживаемой кнопки

1. Нажатие можно получить программно.
2. При нескольких кнопках система может определить, какая именно нажата.
3. Устройство имеет стабильный идентификатор либо уникальный логический номер.
4. Одновременная работа требуемого количества устройств подтверждена испытанием.
5. Есть документированный способ восстановления соединения.
6. Нажатие не требует постоянной работы закрытой программы производителя, через которую JoyRest не может получить событие.
7. Повторные события и дребезг можно отличить или отфильтровать.

### 6.2. Bluetooth: различать типы устройств

**BLE с доступным сервисом/характеристикой:** потенциально поддерживается локальной программой.
**Bluetooth HID-клавиатура:** поддерживается только если программа может различать устройства; одинаковый `Enter` от всех кнопок недостаточен.
**Кнопка с одним событием без идентификатора:** подходит только как одна общая кнопка и не подходит для MVP нескольких команд.
**Устройство только с закрытым приложением:** не считается поддерживаемым, пока не подтверждён доступ к событиям.

### 6.3. USB-комплект

Предпочтение комплектам, у которых:

- один приёмник обслуживает несколько кнопок;
- событие содержит номер кнопки;
- есть открытый протокол, HID-отчёты или поддерживаемый SDK;
- кнопки можно включать и проверять независимо;
- есть индикация заряда/связи либо понятная аппаратная индикация;
- не требуется интернет для локальной работы комплекта.

### 6.4. Подсветка, звук и вибрация

Возможности делятся на:

- обязательные: событие нажатия, идентификатор, состояние подключения;
- желательные: подтверждение нажатия светом, цвет команды, заряд;
- необязательные: звук, вибрация, дисплей.

JoyRest не должен обещать подсветку, пока конкретный адаптер не сообщил поддержку этой возможности.

## 7. Общая архитектура

```text
┌───────────────────────┐       ┌───────────────────────┐
│ Bluetooth-кнопки      │       │ USB-комплект          │
└───────────┬───────────┘       └───────────┬───────────┘
            │                               │
            ▼                               ▼
┌─────────────────────────────────────────────────────────┐
│ Локальная программа «JoyRest Кнопки»                    │
│ BluetoothAdapter / UsbReceiverAdapter                   │
│ нормализация, идентификация, reconnect, diagnostics     │
└───────────────────────────┬─────────────────────────────┘
                            │ локальный защищённый канал
                            ▼
┌─────────────────────────────────────────────────────────┐
│ Пульт JoyRest                                           │
│ привязки, проверка, виртуальный эмулятор, статусы       │
└───────────────────────────┬─────────────────────────────┘
                            │ host-only HTTPS API
                            ▼
┌─────────────────────────────────────────────────────────┐
│ Fastify + PostgreSQL                                    │
│ hardware_bindings + answers + server time + Hub         │
└───────────────────────────┬─────────────────────────────┘
                            │ существующий SSE
                            ▼
┌─────────────────────────────────────────────────────────┐
│ Очередь на пульте / экран зала / телефоны участников    │
└─────────────────────────────────────────────────────────┘
```

### 7.1. Принцип разделения ответственности

**Локальная программа знает:** устройство, источник, идентификатор, связь, батарею, возможности оборудования.
**Пульт знает:** текущую сессию, участников, привязки, какой режим сейчас активен.
**Сервер знает:** кто ведущий, открыт ли подходящий вопрос, какая привязка действительна, какой ответ принят первым.
**Механики знают:** как показать очередь, кому слово и как начислить очки.

Ни один компонент не должен выполнять чужую задачу.

## 8. Локальный канал: обязательный технический этап до основной разработки

До реализации UI и серверной части нужно подтвердить работающий способ связи HTTPS-пульта с локальной программой на целевых операционных системах и браузерах.

### 8.1. Предпочтительный вариант для исследования

Loopback-канал на `127.0.0.1` с:

- WebSocket или HTTP/SSE;
- одноразовым кодом сопряжения;
- проверкой разрешённого origin;
- короткоживущим локальным токеном;
- отсутствием доступа к cookie JoyRest;
- явным статусом подключения в пульте.

### 8.2. Что обязательно проверить

- не блокируется ли канал правилами HTTPS/mixed content;
- требования Private Network Access и preflight;
- поведение после перезапуска программы;
- поведение при нескольких открытых вкладках пульта;
- работу на целевых версиях Windows и macOS;
- отсутствие доступа посторонней веб-страницы к событиям кнопок.

### 8.3. Запасной вариант

Если прямой loopback-канал не проходит требования целевых браузеров, до продолжения основной разработки выбрать и зафиксировать один вариант:

1. браузерное расширение с native messaging;
2. локальное desktop-приложение с изолированным webview/preload IPC;
3. серверный канал с отдельным ограниченным hardware-token.

**Нельзя начинать массовую реализацию на непроверенном предположении, что HTTPS-страница всегда сможет обратиться к локальной программе.**

## 9. Интерфейс пульта

### 9.1. Расположение

В пульте появляется раздел **«Кнопки»**. Внутри него три последовательных режима:

1. **Настройка**.
2. **Проверка**.
3. **Игра** — игровая очередь остаётся в основном интерфейсе соответствующей механики, а не становится отдельной игрой.

В макете эти режимы показаны переключателями «Настройка / Проверка / Игра». В production встраивание должно следовать существующей навигации пульта и не дублировать основную кнопку механики.

### 9.2. Верхний статус

Показывает:

- запущена ли локальная программа;
- есть ли связь пульта с программой;
- количество Bluetooth-устройств;
- количество USB-кнопок;
- число назначенных;
- число назначенных устройств на связи.

Примеры:

- `JoyRest Кнопки запущена`.
- `Нет связи с программой на этом компьютере`.
- `Bluetooth: 3 · USB: 4`.
- `Назначено: 6 из 7`.
- `На связи: 5 из 6`.

### 9.3. Сводка готовности

Состояния:

- **«Всё готово»** — каждый участник имеет кнопку и все назначенные кнопки на связи.
- **«Нужна настройка»** — есть неназначенные участники.
- **«Есть проблема связи»** — привязки полные, но хотя бы одна кнопка отключена.
- **«Программа не подключена»** — аппаратные действия недоступны, телефоны продолжают работать.

### 9.4. Таблица участников

Колонки:

- команда/игрок;
- кнопка и понятное имя;
- источник;
- состояние связи;
- действия.

На узком экране таблица превращается в карточки, без горизонтального скролла всей страницы.

### 9.5. Основные действия

- **«Назначить по очереди»** — главный сценарий.
- **«Добавить Bluetooth»**.
- **«Добавить USB»** или **«Подключить приёмник»**.
- **«Проверить кнопки»**.
- **«Назначить» / «Изменить»** у участника.
- **«Отвязать»**.
- **«Переподключить»** при потере связи.

### 9.6. Технические детали

MAC-адреса, UUID сервисов, HID report ID и другие значения не выводятся в основной список. Они доступны только в диагностике.

## 10. Подключение Bluetooth-кнопки

### 10.1. Первичная установка

1. Ведущий устанавливает «JoyRest Кнопки».
2. Запускает программу.
3. Открывает пульт JoyRest на том же компьютере.
4. Выполняет одноразовое локальное сопряжение программы и пульта.
5. Видит статус «JoyRest Кнопки запущена».

Установка не требуется перед каждой игрой.

### 10.2. Добавление устройства

1. Ведущий нажимает «Добавить Bluetooth».
2. Интерфейс просит перевести кнопку в режим сопряжения по инструкции производителя.
3. Программа выполняет поиск.
4. Найденные устройства показываются списком.
5. Ведущий выбирает устройство.
6. JoyRest просит нажать физическую кнопку для подтверждения.
7. Устройство получает понятное имя «Кнопка N».
8. Далее ведущий назначает его участнику.

### 10.3. Повторное подключение

- Программа пытается восстановить знакомые устройства.
- Привязка остаётся видимой, даже если устройство не найдено.
- Статус меняется локально: `подключаемся → на связи / нет связи`.
- Пульт не создаёт новую привязку после каждого reconnect.
- Если операционная система выдала новый внутренний идентификатор, адаптер должен предложить сопоставление через физическое нажатие, а не молча привязать другую кнопку.

---

## 11. Подключение USB-комплекта

1. Ведущий подключает приёмник.
2. Адаптер определяет поддерживаемую модель.
3. JoyRest показывает «USB-приёмник подключён».
4. При нажатии каждой кнопки адаптер получает её логический номер.
5. Устройство появляется как «USB №N».
6. Назначение выполняется тем же интерфейсом, что и Bluetooth.

### 11.1. Два технических пути

**Прямой WebHID:** допускается после отдельной проверки конкретного приёмника и целевых браузеров.
**Через локальную программу:** основной универсальный путь для SDK, закрытых драйверов и моделей с особыми HID-отчётами.

Продуктовый интерфейс не должен меняться в зависимости от выбранного технического пути.

### 11.2. Неподдерживаемый приёмник

Показать:

> «Этот приёмник пока не поддерживается. Можно использовать Bluetooth-кнопки или телефоны».

В диагностике сохранить техническую причину без персональных данных.

---

## 12. Назначение кнопок по очереди

### 12.1. Запуск

Ведущий нажимает «Назначить по очереди».

- По умолчанию начинается с первого участника без кнопки.
- Если кнопки есть у всех, действие предлагает переназначение с первого участника.
- Вверху видно «Команда N из M».
- Текущий участник выделяется названием и цветом команды.

### 12.2. Ожидание нажатия

Текст:

> «Попросите команду нажать свою физическую кнопку».

В этом режиме:

- принимаются события только от устройств на связи;
- игровые ответы не создаются;
- очки и очередь не меняются;
- одно и то же физическое нажатие обрабатывается один раз;
- повтор удержанием не должен перескочить через несколько команд.

### 12.3. Успешное назначение

Показать:

- «Кнопка назначена»;
- название участника;
- имя и источник кнопки;
- действие «Следующая команда»;
- при поддержке — краткую подсветку цветом команды.

Автоматический переход допускается только после явного подтверждения ведущего в MVP. Это снижает риск случайного двойного перехода.

### 12.4. Пропуск и завершение

- «Пропустить» переходит к следующему участнику без изменения текущей привязки.
- «Закончить» закрывает режим и сохраняет уже выполненные привязки.
- После последнего участника действие называется «Завершить назначение».
- После завершения предлагается перейти к проверке.

### 12.5. Конфликт

Если нажатая кнопка уже принадлежит другому участнику:

> «Эта кнопка уже назначена команде “Зайцы”».

Действия:

- «Выбрать другую кнопку»;
- «Переназначить» с явным подтверждением.

При переназначении прежний участник остаётся без физической кнопки. Одновременной привязки одной кнопки к двум участникам быть не должно.

---

## 13. Ручное назначение и изменение

### 13.1. Новая привязка

1. В строке участника нажать «Назначить».
2. Нажать физическую кнопку либо выбрать обнаруженное устройство.
3. Подтвердить.
4. Увидеть кнопку в строке участника.

### 13.2. Замена кнопки участника

При назначении новой кнопки:

- старая кнопка становится свободной;
- новая закрепляется за участником;
- операция сохраняется как одно логическое изменение;
- после ошибки сохранения интерфейс не должен показывать несуществующую привязку как подтверждённую.

### 13.3. Отвязка

- Не удаляет участника.
- Не удаляет физическое устройство из программы.
- Не удаляет прошлые игровые ответы.
- Не меняет очки.
- Делает кнопку свободной для повторного назначения.

### 13.4. Удаление участника

При удалении участника из сессии его привязка удаляется или помечается недействительной каскадно. Нажатие освободившейся кнопки больше не должно создавать ответ удалённого участника.

---

## 14. Режим проверки

### 14.1. Назначение

Проверка подтверждает три вещи:

1. кнопка на связи;
2. событие доходит до пульта;
3. кнопка назначена правильному участнику.

### 14.2. Экран

- Список всех участников.
- Состояния: «Не назначена», «Нет связи», «Ожидает нажатия», «Нажатие получено».
- Прогресс `получено X из Y`.
- Действие «Начать заново».
- Действие «Завершить проверку».
- Подсказка: «Очки и очередь не меняются».

### 14.3. Поведение

- Каждое валидное нажатие подсвечивает участника.
- Повторное нажатие обновляет визуальное подтверждение, но не увеличивает счётчик уникальных участников.
- Непривязанная кнопка показывает отдельное сообщение и не засчитывается.
- Отключённая кнопка не может быть отмечена как проверенная.
- Проверка не пишет в `answers` и не публикует игровое событие.
- Для диагностики можно записывать локальный `lastTestAt`, но не в основную игровую логику.

### 14.4. Критерий завершения

JoyRest может рекомендовать завершить проверку только когда все назначенные кнопки на связи и дали тестовое нажатие. Ведущий всё равно может продолжить с проблемой, если выбрал резерв.

---

## 15. Игровой режим

### 15.1. До открытия вопроса

- Физические кнопки могут оставаться включёнными.
- Нажатия не попадают в ответы.
- Интерфейс может показать «Раннее нажатие не засчитано».
- Фальстарт не создаётся автоматически.
- Правила конкретной механики не меняются.

### 15.2. Открытие приёма

Приём доступен только когда одновременно выполнены условия:

1. сессия в `playing`;
2. текущий этап допускает ответ;
3. вопрос не раскрыт;
4. время не вышло по серверным правилам;
5. текущая механика действительно поддерживает «кто первый»;
6. участник привязан и существует в сессии;
7. участник допущен к этому розыгрышу;
8. для «Сто к одному» участник входит в текущую пару;
9. для «Ставки на знания» режим клетки и `armed` разрешают нажатие;
10. для квиза текущий вопрос имеет тип `buzz`.

**Любой открытый вопрос не должен автоматически считаться buzz-вопросом.**

### 15.3. Принятие нажатия

- Пульт отправляет `bindingId` и уникальный `eventId`.
- Сервер по привязке определяет `participantId`.
- Сервер ещё раз загружает свежую сессию.
- Сервер проверяет права и текущий шаг.
- Сервер ставит время.
- В `answers.value` записывается ровно `{ buzz: true }`.
- Метаданные источника хранятся отдельно, не ломая существующий парсер значения.
- Публикуется существующее событие ответа.
- Механика синхронизирует очередь.

### 15.4. Повторное нажатие

- Не меняет место.
- Не меняет `submitted_at`.
- Не создаёт второй ответ.
- Не переносит участника в конец.
- Может показать локальное подтверждение «Уже в очереди».

### 15.5. Ответ ведущего

**«Верно»:** используется существующее завершение шага и начисление.
**«Неверно»:** используется существующий `buzzWrong`; слово переходит следующему.
**Очередь закончилась:** механика действует по своему паспорту; аппаратная подсистема не выдумывает новый исход.

### 15.6. Следующий вопрос и «Назад»

- На новом шаге привязки сохраняются, очередь очищается по правилам механики.
- При «Назад» используется существующая очистка/замена ответов.
- Запоздалый ответ с прежнего шага не должен попасть в новый показ.
- Повторный показ того же вопроса образует новый допустимый слот по существующему `startedAt`.
- Событие со старым `eventId` не должно воскрешать старый ответ.

## 16. Смешанный ввод и резерв

### 16.1. Bluetooth + USB

Оба источника равноправны. Порядок зависит от серверной записи, а не от типа устройства.

### 16.2. Физическая кнопка + телефон

- Оба пути приводят к одному участнику и одному ответу на шаг.
- Побеждает первый принятый сервером.
- Повтор через другой источник не меняет ответ.
- Не должно быть отдельных мест «за Bluetooth» и «за телефон» в одной очереди.

### 16.3. Потеря связи

При отключении:

1. привязка сохраняется;
2. участник получает статус «Нет связи»;
3. ведущий видит предупреждение;
4. телефон остаётся доступным по правилам механики;
5. ведущий может переподключить или заменить кнопку;
6. уже принятые ответы не отменяются.

### 16.4. Ручной резерв

Если у участника нет телефона и кнопка отключилась, ведущий может использовать существующие инструменты управления игрой. Отдельное действие «Нажать за команду» добавлять только после отдельного продуктового решения, поскольку оно влияет на честность очереди и должно явно маркироваться как ручное.

## 17. Серверная модель данных

Точные имена и типы согласовать с актуальными миграциями; типы внешних ключей должны соответствовать существующим таблицам.

### 17.1. `hardware_bindings`

Рекомендуемые поля:

| Поле | Назначение |
|---|---|
| `id` | `bindingId`, случайный идентификатор |
| `session_id` | Сессия JoyRest |
| `participant_id` | Существующий игрок или команда |
| `source` | `bluetooth` или `usb` |
| `hardware_id` | Стабильный ID внутри источника |
| `alias` | Понятное имя «Кнопка 1» / «USB №2» |
| `created_at` | Время создания |
| `updated_at` | Последнее изменение |

Ограничения MVP:

- `unique(session_id, source, hardware_id)`;
- `unique(session_id, participant_id)`;
- внешние ключи на сессию и участника;
- удаление сессии удаляет привязки;
- удаление участника не оставляет активную привязку.

### 17.2. Расширение `answers`

Через отдельную обратно совместимую миграцию:

- `source` со значением по умолчанию для существующих телефонных ответов;
- опционально `hardware_event_id` для идемпотентности и диагностики;
- опционально `hardware_binding_id`.

Существующее поле `value` не меняет формат. Старые клиенты должны продолжать читать ответы без обязательного знания новых полей.

### 17.3. `uid` аппаратного ответа

Сохранить существующую семантику доступа:

- если у участника есть текущий капитан/владелец устройства, использовать соответствующий существующий `uid`;
- если участник создан без телефона, техническое значение выбрать при реализации так, чтобы чтение ответа не открывало его постороннему;
- автором действия для аудита считается ведущий сессии, а не кнопка;
- не выдавать кнопке самостоятельную гостевую личность.

Этот пункт требует отдельного теста `canReadAnswer` до реализации.

### 17.4. Что не хранить в PostgreSQL постоянно

- каждое изменение заряда;
- каждый reconnect;
- высокочастотные heartbeat;
- локальные HID/BLE-данные;
- технические журналы программы с произвольными системными путями.

## 18. Серверные API

Все маршруты доступны только ведущему сессии или роли, которой уже разрешено управление ею. Использовать существующий `hostedSession`/общие permissions, не создавать отдельную проверку «по знанию ID».

### 18.1. Получить привязки

```http
GET /api/sessions/:id/hardware-bindings
```

Возвращает привязки текущей сессии без технических секретов.

### 18.2. Создать или изменить привязку

```http
PUT /api/sessions/:id/hardware-bindings/:bindingId
```

Тело содержит источник, `hardwareId`, `participantId`, `alias`.

Сервер проверяет:

- сессия не завершена;
- участник принадлежит сессии;
- ограничения уникальности;
- допустимую длину и алфавит идентификаторов;
- отсутствие привязки к участнику другой сессии.

### 18.3. Удалить привязку

```http
DELETE /api/sessions/:id/hardware-bindings/:bindingId
```

Операция идемпотентна: повторное удаление не должно приводить к повреждению состояния.

### 18.4. Игровое нажатие

```http
POST /api/sessions/:id/hardware-buzz
```

Тело:

```json
{
  "bindingId": "…",
  "eventId": "…",
  "localPressedAt": 0
}
```

`localPressedAt` необязателен и используется только для диагностики. Клиент не передаёт `submittedAt` и не определяет победителя.

Ответы:

- `sent` — ответ сохранён;
- `duplicate` — это событие уже обработано;
- `rejected` — шаг закрыт, привязка недействительна, участник не допущен или ответ уже существует;
- `conflict` — состояние изменилось, требуется свежий снимок;
- стандартные `401`, `403`, `404`, `400` по правилам сервера.

### 18.5. Транзакция и блокировки

При записи:

- использовать свежее состояние сессии под существующей блокировкой;
- сохранять ответ атомарно;
- не допускать принятого, но не учтённого ответа при одновременном закрытии вопроса;
- публиковать Hub-событие только после успешной записи;
- повтор `eventId` не должен публиковать второй ответ.

## 19. Локальный протокол программы

Независимо от транспорта логические сообщения единые.

### 19.1. Возможности

```json
{
  "type": "capabilities",
  "version": 1,
  "adapters": ["bluetooth", "usb"],
  "features": ["press", "battery", "led"]
}
```

### 19.2. Устройство появилось или изменилось

```json
{
  "type": "device",
  "source": "bluetooth",
  "hardwareId": "…",
  "connected": true,
  "battery": 84,
  "features": ["press", "led"]
}
```

### 19.3. Нажатие

```json
{
  "type": "press",
  "source": "usb",
  "hardwareId": "…",
  "eventId": "уникальный-id",
  "localPressedAt": 0
}
```

### 19.4. Правила событий

- `eventId` создаётся один раз на физическое нажатие и сохраняется при повторной доставке.
- Отпускание кнопки не считается вторым нажатием.
- Удержание не создаёт поток новых игровых ответов.
- Адаптер выполняет минимально необходимый аппаратный debounce и не добавляет искусственную задержку.
- Программа не решает, кто победил.
- Программа не знает правильный ответ и очки.
- Повторная доставка после reconnect использует тот же `eventId`.

## 20. Восстановление и жизненный цикл

### 20.1. Обновление страницы

- Привязки загружаются с сервера.
- Пульт заново соединяется с локальной программой.
- Устройства сопоставляются по `source + hardwareId`.
- Неизвестные устройства не назначаются автоматически.
- Текущая очередь приходит из существующего состояния и ответов, а не из локальной памяти.

### 20.2. Перезапуск программы

- Сессия и привязки не удаляются.
- Пульт показывает временную потерю локальной связи.
- После запуска связь восстанавливается.
- Нажатия во время отсутствия программы не считаются гарантированно сохранёнными; интерфейс не должен обещать их восстановление.

### 20.3. Завершение сессии

- Привязки больше не принимают игровые события.
- API возвращает отказ.
- Локальная программа может продолжать видеть устройства, но они не влияют на завершённую игру.

### 20.4. Новая сессия

Привязки не переносятся незаметно. В последующей версии можно предложить «Повторить прошлую раскладку» только с явным сопоставлением новых участников и тестовым нажатием.

## 21. Состояния и тексты ошибок

| Ситуация | Основной текст | Доступные действия |
|---|---|---|
| Программа не установлена | «Для физических кнопок установите JoyRest Кнопки» | Инструкция; продолжить с телефонами |
| Нет локальной связи | «Нет связи с программой на этом компьютере» | Переподключить; диагностика |
| Кнопка не найдена | «Не удалось найти кнопку» | Повторить поиск; проверить режим сопряжения |
| Неподдерживаемая модель | «Эта модель пока не поддерживается» | Другой источник; телефон |
| Кнопка не назначена | «Кнопка не назначена команде» | Назначить; отвязать |
| Кнопка занята | «Эта кнопка уже назначена другой команде» | Отмена; переназначить |
| Нет связи с кнопкой | «Нет связи. Привязка сохранена» | Переподключить; телефон |
| Нажатие до старта | «Раннее нажатие не засчитано» | Запустить отсчёт |
| Повтор | «Команда уже в очереди» | Ничего не менять |
| Неподходящий шаг | «На этом шаге физическая кнопка не используется» | Вернуться к правилам игры |
| Ответ уже закрыт | «Вопрос уже закрыт» | Следующий шаг |
| Ошибка сервера | «Нажатие не подтверждено» | Повтор с тем же eventId; проверка ответа |
| Firebase | «Физические кнопки доступны только на собственном сервере» | Телефоны |

Ошибка не должна исчезать раньше, чем ведущий сможет её прочитать, если требуется действие.

## 22. Безопасность и приватность

1. Все серверные операции привязок и нажатий — host-only.
2. `bindingId` и `hardwareId` не являются авторизацией.
3. Локальная программа не получает пароль ведущего и cookie сессии.
4. Локальный канал требует сопряжения и проверки origin.
5. Посторонняя веб-страница не должна читать локальные устройства или отправлять нажатия.
6. Клиент не может подставить произвольного участника в обход серверной привязки.
7. Клиент не может подставить прошлое или будущее серверное время.
8. Гостевой SSE не должен получать технические идентификаторы оборудования и привязки.
9. В Telegram не отправлять имена гостей, идентификаторы устройств или содержимое игровых событий.
10. Журналы не должны содержать пароли, cookie, токены сопряжения, полные персональные данные.
11. Доступ гостя к своему ответу проверить отдельно при аппаратном источнике.
12. Миграции следуют expand/contract и не ломают старое чтение ответов.

## 23. Производительность и честность очереди

### 23.1. Принципы

- Не добавлять анимационную задержку перед отправкой нажатия.
- Не ждать подсветки или звука для записи ответа.
- Не отправлять heartbeat в таблицу ответов.
- Не делать опрос сервера на каждое локальное событие состояния.
- Использовать существующий SSE для результата.
- Не полагаться на синхронность часов ПК и сервера для победителя.

### 23.2. Что измерять на стенде

- от физического нажатия до события адаптера;
- от адаптера до пульта;
- от пульта до подтверждения сервера;
- от записи до появления в очереди;
- долю повторных/потерянных событий;
- поведение при одновременном нажатии всех кнопок;
- reconnect после сна ноутбука;
- продолжительную работу на полном мероприятии.

Численный production-бюджет зафиксировать после первого аппаратного стенда по измерениям, а не обещать произвольную задержку заранее.

### 23.3. Одновременные нажатия

При совпадении серверного времени используется существующее детерминированное разрешение порядка. Нельзя показывать разный порядок на разных устройствах. Все клиенты получают одну серверную последовательность.

## 28. Обязательные автотесты

### 28.1. Сервер

- ведущий сессии может создать привязку;
- другой ведущий не может;
- гость не может;
- участник из другой сессии не может быть привязан;
- одна кнопка не может принадлежать двум участникам;
- один участник не получает две активные кнопки в MVP;
- замена освобождает старую кнопку;
- удаление участника отключает привязку;
- нажатие только на текущем подходящем buzz-шаге;
- отказ после reveal;
- отказ после завершения;
- отказ после таймера с существующим grace;
- отказ участника вне текущей пары «Сто к одному»;
- повтор `eventId` не дублирует ответ;
- повтор участника не меняет время;
- одновременные нажатия не теряются;
- закрытие вопроса не теряет уже принятый ответ;
- старый `eventId` не попадает в новый шаг;
- «Назад» и повторный показ работают по существующим правилам;
- Hub получает одно событие после успешной записи;
- старый формат `{ buzz: true }` продолжает работать;
- гость видит только разрешённый ответ;
- удаление сессии очищает привязки.

### 28.2. Локальная программа

- каждое устройство имеет правильный источник и ID;
- отпускание не считается нажатием;
- удержание не создаёт лавину событий;
- reconnect сохраняет идентичность;
- повторная доставка сохраняет `eventId`;
- две одинаковые модели различаются;
- USB №1 не путается с USB №2;
- неподдерживаемое устройство не отправляет ложные события;
- посторонний origin не получает доступ;
- программа не сохраняет cookie JoyRest.

### 28.3. UI

- пустое состояние;
- частичное назначение;
- полное назначение;
- назначение по очереди;
- пропуск участника;
- ручное назначение;
- конфликт и отмена конфликта;
- замена и отвязка;
- проверка без записи ответа;
- раннее нажатие;
- повторное нажатие;
- телефон + кнопка;
- Bluetooth + USB;
- потеря связи;
- обновление страницы;
- закрытие модальных окон с клавиатуры;
- 375 px без общего горизонтального скролла.

## 29. Ручные сценарии приёмки

### Сценарий A. Первая настройка

1. Кнопка назначена не той команде.
2. Ведущий выбирает «Изменить».
3. Нажимает правильную кнопку.
4. При конфликте видит предупреждение.
5. После подтверждения старая связь исчезает.
6. Проверка подтверждает новую раскладку.

### Сценарий C. Раннее и повторное нажатие

1. До отсчёта нажатие не попадает в ответы.
2. После отсчёта первое нажатие принято.
3. Повтор не меняет место и время.
4. Нажатие с телефона той же команды также не создаёт второй ответ.

### Сценарий D. Одновременность

1. Несколько источников нажимаются почти одновременно.
2. Все принятые события появляются один раз.
3. Пульт, экран и телефоны видят согласованный результат.
4. После повторного прогона нет расхождения состояния.

### Сценарий E. Потеря связи

1. Назначенная кнопка отключается.
2. Привязка остаётся.
3. Ведущий видит предупреждение.
4. Команда отвечает телефоном.
5. Кнопка возвращается и работает на следующем шаге без новой привязки.

### Сценарий F. Сбой программы

1. Программа закрывается перед вопросом.
2. Пульт сообщает о локальной потере связи.
3. Телефоны продолжают работать.
4. После перезапуска программы привязки и устройства восстанавливаются.

### Сценарий G. Команда без телефона

1. Ведущий добавляет команду без телефона.
2. Назначает ей физическую кнопку.
3. Нажатие принимается host-only маршрутом.
4. Очки начисляются существующей механикой.
5. Посторонний гость не может читать или подделать это событие.
